## Problem space — authorization serves three substrates

What began as "privilege elevation" for host commands (`sudo`) is architecturally an **Authorization Provider** that
happens to cover operating system privilege escalation alongside cloud identity federation, service authentication, and
sandbox boundary governance. Authorization exists to serve three distinct execution substrates. Each has its own
*sometimes-authorized, sometimes-baseline* character, and the design owes a unified capability model to all three.

### Substrate 1 — command execution

Four providers run host commands; whether a given command requires elevated host authority depends on the command and
the target platform.

| Provider method | Spawn path today | Authorization — example |
|---|---|---|
| `shell.Provider.Exec` (`pkg/op/provider/shell/provider.go:51`) | `sh -c` via the runtime `Runner` | `shell.exec("ls")` none; `apt-get install` sudo |
| `powershell.Provider.Exec` (`pkg/op/provider/powershell/provider.go:60`) | `pwsh -Command` via the runtime `Runner` | installing a Windows service — Administrator / UAC |
| `pkg.Provider.Install` / `Remove` / `Upgrade` (`pkg/op/provider/pkg/provider.go:53`) | platform manager router → `pkg/platform.runCommand(argv, sudo)` (corrected 2026-10-21: a package var at `helpers_unix.go:58`) | Homebrew none (brew runs unprivileged); apt, MacPorts sudo |
| `service.Provider.Start` / `Stop` / `Enable` / `Disable` / `Restart` (`pkg/op/provider/service/provider.go:184`) | platform init backend → the same `runShellCommand` | systemd sudo; a launchd **user** agent none |

The *sometimes / sometimes-not* is modeled as per-backend `NeedsSudo()` — systemd true (`pkg/platform/linux_managers.go:168`),
SysVinit true (`:188`), a launchd user agent false (`pkg/platform/darwin_managers.go:79`), the Windows service control
manager true (`windows_managers.go:38`) — and **nothing calls it** (corrected 2026-10-21): every privileged call site
passes a literal `true` to `runCommand(argv, sudo bool)`, which inlines `sudo -n` under a standing TODO to replace that
inline with the authorization model — *"centralize this. Route privileged execution through the ElevationOffer/Elevator
-- one credential-cached, policy-governed, audited sudo session -- instead of every command inlining `sudo -n`"*
(`pkg/platform/helpers_unix.go:70-71`). On Windows the equivalent is `runWindowsCommand(command, elevated)`
(`windows_managers_windows.go:268`), whose elevation is `Start-Process -Verb RunAs`, the UAC dialog. Ruled
2026-10-21: both go; the backend declares the account its commands need and obtains the runner standing for it
([`6.2`](6.2-process-pool.md) § 4.1).

This substrate poses two questions:

1. **Process management.** Scattered one-shot spawns — shell / pwsh via the runtime `Runner`, pkg / service via
   `runShellCommand` — each build a fresh `*exec.Cmd`. How do we manage the processes these providers rely on?
2. **Host Escalation.** When a command must run under an account other than the caller's, how do we authorize and
   execute it? Answered 2026-10-21: a session on the runner daemon standing for that account ([`6.2`](6.2-process-pool.md)),
   granted by this provider through the broker ([`2.7`](2.7-control-plane.md)).

### Substrate 2 — network & service access

Providers that reach remote network resources, cloud APIs, or external services and require a credential or delegated
token to do so.

| Provider method | Today | Grant — example |
|---|---|---|
| `appnet.Provider.Download` (`pkg/op/provider/appnet/provider.go:41`) | bare `http.DefaultClient`, no credential | public URL none; private registry / artifact store — bearer token or signed header |

### Substrate 3 — sandboxed agent & workload execution (`sbx`)

When orchestrating autonomous agents or untrusted workloads inside microVM sandboxes (such as Docker `sbx`),
authorization spans multiple independent trust boundaries simultaneously:

| Trust boundary | Requirement | Grant — example |
|---|---|---|
| **Sandbox runtime (`sbx`)** | Host-side authentication to the sandbox control plane | Docker ID (`sbx login`) session or organization governance lease |
| **Model & MCP endpoints** | Agent access to LLM providers (Anthropic, OpenAI, Gemini) and MCP servers | Ephemeral API keys or OAuth bearer tokens injected into the sandbox environment |
| **Cloud & repo targets** | Agent operations against customer infrastructure (AWS, GCP, GitHub) | Short-lived STS `AssumeRole` credentials or fine-grained installation tokens |
| **Host boundary bridge** | Controlled escape hatches from the sandbox to the host | Pre-authorized IPC socket or scoped `ProcessSpawn` execution handle |

The point of `authz.Provider`: **any provider method or sandboxed workload that requires authority can be passed
an `Grant`.** `authz.Provider` is the single authority source — it acquires a host escalation
session or mints/leases a credential grant from a configured broker (sudo/polkit, Docker `sbx`, AWS STS, Vault,
Kubernetes, OS keychain), passes the `Grant` by-value into the consuming node's input slot, and records an
`Lease` so the grant is deterministically audited and revoked on completion or rollback.

### Unifying the substrates

Rather than treating OS privilege escalation as a separate vertical concept ("elevation") and API token acquisition as a
separate horizontal concept ("authentication"), both are strategies of **Authorization**:

- **`IdentityAssumption`** (today a string constant of the dormant `op.ElevationOffer` in `pkg/op/elevation_policy.go`;
  corrected 2026-10-21) acquires a credential-bearing `Grant` that
  can be consumed by *any* substrate — injected as `MaskedVars` into a command or `sbx` microVM, or attached as
  headers/bearer tokens to an `appnet` request.
- **`ProcessSpawn`** acquires a host-escalation `Grant` that is a **session on the runner** standing for the requested
  account, for Substrate 1 (and host-side Substrate 3 setup). Ruled 2026-10-21: no worker, no wrapper; `sudo`, `doas`,
  `runas` and the Windows service are how the *runner* comes to exist ([`6.2`](6.2-process-pool.md) § 10), not what a
  command carries.
- **`InteractiveChallenge`** and **`MandatedApproval`** gate *either* mechanism behind a human prompt (TTY / WebAuthn /
  device code) or an asynchronous gatekeeper ticket via the pause/resume machinery.

Authorization **acquires** a time-bound capability (`Grant`); the substrate **consumes** it.

## Thesis

Authorization is a **multi-party, just-in-time** mechanism, deliberately split across three owners — and that split is
the whole point: it keeps the operation graph an immutable, environment-agnostic artifact while the *how* of
authorization lives in the environment configuration, owned by the platform/security team or host operator, not the
graph author.

One **`authz`** package (`pkg/op/provider/authz`) holds both the contract — the policy and broker interfaces
(`authz.Policy`, `authz.Broker`, `authz.BrokerConfig`) — and the **provider** that fulfills the *how* across all
strategies (`authz.Provider`). Following the settled broker router architecture
([`3.2-projected-provider-api.md`](3.2-projected-provider-api.md#pluggable-brokers--provider-owned-routers)),
`authz.Provider` owns an internal broker router constructed directly from the profile-resolved `authz.ProviderConfig`
tree — with zero global driver registries or `init()` self-registration. The router is itself a `Broker`, and the
pattern is recursive (corrected 2026-10-21 to 3.2's rule: a sub-broker may be a router).

**Under the broker (ruled 2026-10-21).** This provider runs in the caller's process and is the **client side** of
authorization: it resolves the unit's offer, asks the broker ([`2.7`](2.7-control-plane.md) § Authorization at the
socket) for the account, and receives a grant or a named refusal. The broker holds the policy — which peers may ask for
which accounts — in *its own* profile, decides at the socket by the peer's uid (locally) or the token (remotely), and
spawns. Where `offers` and `brokers` are configured — the caller's profile, the broker's, or both — is open
(§ Open).

## The three-way split (graph / configuration / runtime environment)

| Owner | Carries | When | devlore home |
|---|---|---|---|
| **Graph** | the *requirement* — a **named offer** (`offer_reference_id`) + `requested_ttl`, target scope, context assertions | design/plan-time; saved into the immutable, signed graph | the plan (`authorize` node input) |
| **Configuration** | the *provisioning* — per-profile realization of named offers → configured broker instances | profile resolution (local / sbx / dev / stage / prod) | `authz.ProviderConfig`, the `providers.authz` section (§ The config shape) |
| **RuntimeEnvironment** | the *instantiated provider router* + live grant acquisition & lease revocation | bootstrap + node execution + compensation | held on `RuntimeEnvironment`, built from resolved `Application.Config` |

**Separation of duties.** Graph authors declare *what* authority a node or subgraph requires; platform teams or host
configurations define *how* that authority is realized in each environment. *"The graph only knows what it needs, not
how to get it."* A compiled, signed graph promotes from a developer laptop to an `sbx` microVM to a production CI runner
with **zero graph edits** — the same signed artifact resolves against the active profile's
`authz.ProviderConfig`.

This settles the per-unit Policy vs. offer/request/provision question: **adopt the split across the board.** Implicit
host escalation — a `pkg` or `service` backend declaring an account other than the caller's — resolves against a
default host-escalation offer in the active profile (its name, and whether writ's System scope asks by name, is open:
§ Open), while explicit cloud, sandbox, or service authority resolves via named offers (`offer_reference_id`).

## Authorization strategies (modalities)

All strategies are fulfilled by `authz.Provider` and represented as **string enums** (ruled 2026-10-21: strings, for
readability, as [`6`](6-execution-topology.md) § Target design and `BackoffStrategy` already do; the empty string is the
zero value and means "defer to default", so there is no reserved `None`):

```go
// Strategy is the HOW — the mechanism used to acquire an authorization. The empty string defers.
type Strategy string

const (
	ProcessSpawn         Strategy = "process_spawn"         // host escalation: a session on the runner standing for the account
	IdentityAssumption   Strategy = "identity_assumption"   // JIT token / secret brokering: STS, OIDC, Vault, sbx
	InteractiveChallenge Strategy = "interactive_challenge" // synchronous user challenge: TTY prompt, device code, WebAuthn
	MandatedApproval     Strategy = "mandated_approval"     // asynchronous gatekeeper ticket (pauses the unit via ErrPaused)
)
```

- **`ProcessSpawn`** (host escalation) — acquires a **session on the command runner** standing for the requested
  account ([`6.2`](6.2-process-pool.md) § 4.1), through the broker's runner selector
  ([`2.7`](2.7-control-plane.md)). Ruled 2026-10-21: no privileged worker of its own, no `sudo -n` wrapper; the runner
  is the persistent privilege, and the session is both the grant and the lease.
- **`IdentityAssumption`** — **JIT credential and token minting**: an `authorize` action node mints or leases a
  short-lived `Grant` (AWS STS, K8s SA, Vault, SPIFFE/SPIRE, OIDC, Docker `sbx` token, OS keychain secret) and bridges
  it to the units that consume it. The broker's own remote API is this substrate's first consumer
  ([`2.7`](2.7-control-plane.md) § Authorization at the socket).
- **`InteractiveChallenge`** / **`MandatedApproval`** — gatekeeper strategies that **ride the existing pause/resume
  machinery**: when an offer requires interactive login (e.g., an unauthenticated `sbx login` or cloud SSO session) or
  external human approval, the unit pauses (`ErrPaused`) with a ticket/challenge context until satisfied, then resumes.

## The grant bridge & lease compensation

### 1. Forward dataflow: `Grant` over native typed slots

The grant bridge rides devlore's existing **typed slots / edges** ([`2.1-typed-slots.md`](2.1-typed-slots.md)). A
`Grant` minted at an `authorize` node flows along an edge into the consumer unit's input slot — **pass-by-value,
node-owned, memory-zeroed** after use, with `MaskedVars` injected into the target node's execution or sandbox
environment. The security property: **zero shared state** — a crashed parallel branch cannot leak a grant it was never
explicitly bridged.

**Corrected 2026-10-21, and open.** For the process case (`ProcessSpawn`) nothing crosses an edge at all: the `pkg`,
`service` or command provider acquires its runner session through the broker, and the grant is the broker's business.
For identity assumption the property above is not yet true in the tree: an edge exists only for a `PromiseBinding`, and
a promise resolves through `RecoveryStack.ResultByUnitID`, so a producer's result is **retained on the stack by unit id
until unwind** (`pkg/op/binding.go`, `recovery_stack.go`). A grant returned as a result would live in shared, committed
state. Whether a grant travels as a result at all, or the `authorize` node binds it into the consumer's activation
outside the result channel, and what `Zero()` guarantees once a value holding maps has been copied, is § Open.

### 2. Backward unwinding: the `Lease` is the receipt

Every `Authorize` invocation returns both the forward `Grant` and a compensable receipt, the `Lease`. **Corrected
2026-10-21:** every provider action in the tree is `X(activationRecord *op.ActivationRecord, …) (Product, *Receipt,
error)` paired with `CompensateX(activationRecord, *Receipt) error`, and it is the **executor** that commits the receipt
and pushes it onto the `RecoveryStack` (`GraphExecutor.pushAuditReceipt`, `graph_executor.go:1361-1399`); a provider
registers nothing. So the `Lease` is a `Receipt` sealed through `ReceiptBase`, returned, not registered, and
`CompensateAuthorize` is the executor's call during unwind — so that when a subgraph exits or a downstream node fails,
active credentials (Vault leases, runner sessions, temporary sandbox sessions, approval tickets) are deterministically
revoked. For `ProcessSpawn` revocation releases the runner session; there is no sudo timestamp to revoke, because the
runner holds the privilege, not the caller's shell ([`6.2`](6.2-process-pool.md) § 11).

```go
// pkg/op/provider/authz

// GrantKind distinguishes how a consumer substrate applies the Grant. A string enum; the empty string defers.
type GrantKind string

const (
	ProcessSession GrantKind = "process_session" // a session on the runner standing for the account (6.2 § 4.1)
	BearerToken    GrantKind = "bearer_token"    // HTTP Authorization header / API token / OIDC JWT
	CredentialEnv  GrantKind = "credential_env"  // environment bundle (AWS_SESSION_TOKEN, KUBECONFIG, SBX_TOKEN)
	ApprovalTicket GrantKind = "approval_ticket" // signed gatekeeper lease authorizing execution to proceed
)

// Grant — the unified capability bridged down graph edges (identity assumption) or held by the broker (process session).
type Grant struct {
	GrantID    string    `json:"grant_id" yaml:"grant_id"`
	OfferID    string    `json:"offer_id" yaml:"offer_id"`
	Kind       GrantKind `json:"kind" yaml:"kind"`
	Strategy   Strategy  `json:"strategy" yaml:"strategy"`
	IssuedAt   time.Time `json:"issued_at" yaml:"issued_at"`
	ExpiresAt  time.Time `json:"expires_at" yaml:"expires_at"` // strict clock limit for fail-fast node evaluation

	// Credential & Network Payload (IdentityAssumption)
	Value      string            `json:"-" yaml:"-"`                   // raw secret or signed JWT; excluded from plain marshaling
	MaskedVars map[string]string `json:"-" yaml:"-"`                   // env vars injected into target node/sandbox, masked in logs
	Headers    map[string]string `json:"-" yaml:"-"`                   // HTTP headers for appnet / service calls

	// Host Escalation Payload (ProcessSpawn): the runner session the broker holds for this run (6.2 § 4.1)
	RunnerSessionID string `json:"runner_session_id,omitempty" yaml:"runner_session_id,omitempty"`
	Account         string `json:"account,omitempty" yaml:"account,omitempty"` // the account the runner stands for
}

func (g *Grant) IsExpired(now time.Time) bool {
	return !g.ExpiresAt.IsZero() && now.After(g.ExpiresAt)
}

// Zero scrubs sensitive credential material from memory upon consumer completion.
func (g *Grant) Zero()

// Lease — the compensation state: the receipt Authorize returns, committed and pushed by the executor (corrected 2026-10-21).
type Lease struct {
	op.ReceiptBase
	GrantID      string   `json:"grant_id" yaml:"grant_id"`
	OfferID      string   `json:"offer_id" yaml:"offer_id"`
	BrokerName   string   `json:"broker_name" yaml:"broker_name"`
	Strategy     Strategy `json:"strategy" yaml:"strategy"`
	RevokeHandle string   `json:"revoke_handle,omitempty" yaml:"revoke_handle,omitempty"` // JTI, Vault lease ID, or runner session
}
```

## The broker-router mechanism (reconciled with 3.2 & `configuration.md`)

Per [Projected Provider API → Pluggable brokers](3.2-projected-provider-api.md#pluggable-brokers--provider-owned-routers),
there is no global `RegisterDriver` table or `op.BrokerRegistry` trait. Instead:

1. **`authz.Broker` is a standard Go interface.** Any concrete broker (`awsSTSBroker`, `vaultBroker`, `sbxAuthBroker`,
   `osKeychainBroker`, `hostEscalationBroker`) implements `authz.Broker` and pairs with a typed `authz.BrokerConfig`
   node in the config schema.
2. **`authz.Provider` owns a composite router, which is itself a `Broker`** (corrected 2026-10-21 to 3.2's rule). At
   provider initialization, `authz.Provider` reads its resolved `authz.ProviderConfig`, instantiates the configured
   child brokers — a sub-broker may itself be a router — validates that every configured offer maps to an enabled
   broker, and routes `Authorize` and `CompensateAuthorize` calls by offer name.

```go
// pkg/op/provider/authz

// Broker is the interface fulfilled by concrete authorization backends
// (host_escalation, aws_sts, vault, k8s_token, sbx_auth, os_keychain, mandated_approval) and by the router.
type Broker interface {
	Type() string
	Acquire(ctx context.Context, req OfferRequest) (Grant, *Lease, error)
	Revoke(ctx context.Context, lease *Lease) error
}

// Provider fulfills authorization requests across OS escalation, sandbox auth,
// cloud token brokering, and human-in-the-loop approval workflows.
//
// +devlore:access=both
type Provider struct {
	op.ProviderBase
	router Broker // provider-owned router built from the resolved ProviderConfig; a Broker like its leaves
}

func NewProvider(runtimeEnvironment *op.RuntimeEnvironment) *Provider

// Corrected 2026-10-21 to the action convention: the activation record first, the receipt returned, never registered.
func (p *Provider) Authorize(activationRecord *op.ActivationRecord, req OfferRequest) (Grant, *Lease, error)
func (p *Provider) CompensateAuthorize(activationRecord *op.ActivationRecord, lease *Lease) error
```

Because concrete brokers are allocated from the typed `Brokers` subtree on `authz.ProviderConfig`, unknown or
misconfigured broker types fail fast during **config resolution / bootstrap**, long before any graph node executes.

## The config shape (`authz.ProviderConfig`)

The configuration reconciles the three-way split with [`configuration.md`](configuration.md)'s recursive profile tree
(`base` / `profiles` / `applications`). **Corrected 2026-10-21, two ways.** The section's path is `providers.authz`,
as configuration.md addresses every provider (`profiles.release.providers.<name>.brokers…`), not a top-level
`authorization:`. And the recursive tree it embeds is designed, not built: `pkg/devconfig` is still the flat
`Config{sections map[string]Section}` with no `ConfigBase` and no loader (step 38 § Configuration dependency names
this gate). Until the tree lands, `authz.ProviderConfig` follows the one pattern a provider config has in the tree —
`op.PoliciesConfig` (`pkg/op/policies_config.go`): an `init()`-time `AnnounceSection`, `devconfig.SectionBase`
embedded, a typed accessor — and moves to `ConfigBase` when the reshape does. (`encryption.ProviderConfig`, the
draft's naming precedent, is a convention, not a type in the tree.)

**(a) Plan-time — declared on graph nodes, saved into the signed graph (never in config):**

```yaml
# on the authorize action node (or implicit unit requirement)
request:
  offer_reference_id: "off_aws_prod_deployer"     # the NAMED offer (abstract capability handle)
  requested_ttl_seconds: 900
  scope: ["s3:GetObject", "s3:PutObject"]
  required_context_assertions: ["target_environment == 'prod'"]
```

**(b) Profile-resolved provisioning — `authz.ProviderConfig`:**

`authz.ProviderConfig` carries two typed maps (on `SectionBase` today, `ConfigBase` when the tree lands):
1. **`offers`**: Maps each abstract `offer_reference_id` to its `AuthorizationStrategy`, fallback strategy chain,
   maximum TTL policy, and the named broker instance that fulfills it.
2. **`brokers`**: The typed sub-tree of configured broker backends for the active profile.

```yaml
# Resolved via configuration.md profile overlays (base -> profiles.<active> -> providers.authz)
providers:
 authz:
  offers:
    off_host_root:                   # the default host-escalation offer; its name is open (§ Open)
      strategy: process_spawn
      broker: local_runner
      max_ttl_seconds: 300

    off_sbx_runtime:
      strategy: identity_assumption
      fallback_strategies: [interactive_challenge]
      broker: docker_sbx

    off_aws_prod_deployer:
      strategy: identity_assumption
      broker: aws_sts_prod
      max_ttl_seconds: 900

    off_model_anthropic:
      strategy: identity_assumption
      broker: host_keychain_anthropic

  brokers:
    local_runner:
      type: host_escalation          # a session on the runner standing for the account, via the broker daemon (2.7)
      interim: sudo                  # iteration 1 of the schedule: the in-process stub runs `sudo -n` until the runner lands

    docker_sbx:
      type: sbx_auth
      require_org_sso: false

    aws_sts_prod:
      type: aws_sts_assume_role
      connection_timeout_seconds: 10
      role_arn: "arn:aws:iam::123456789012:role/PipelineDeployer"
      region: us-west-2

    host_keychain_anthropic:
      type: os_keychain
      service_name: "devlore/anthropic-api-key"
      env_var_target: "ANTHROPIC_API_KEY"
```

When a customer runs an agent inside an `sbx` sandbox:
- The host's `authz.Provider` resolves `off_sbx_runtime` to verify `sbx` authentication, resolves
  `off_model_anthropic` and `off_aws_prod_deployer` to mint/fetch short-lived grants on the host, and bridges only the
  ephemeral `MaskedVars` into the `sbx` microVM.
- Inside the `sbx` microVM, if the agent runs a sub-graph that requires local package installation (`off_host_root`),
  the profile inside the microVM resolves `off_host_root` to the sandbox's own runner without ever touching the host
  OS.

## Secretless, signed, tamper-evident

The graph artifact is **signed** (integrity + authenticity; see
[`graph-signing.md`](../plans/extract-starlark-from-op/phase-8/graph-signing.md)) and **secretless** — it holds only
the abstract `offer_reference_id`, requested scope, and TTL. `authz.ProviderConfig` holds broker **definitions**
(role ARNs, Vault mount paths, keychain service names) — *never* raw long-lived secrets; actual root credentials come
from the host's ambient trust chain (OIDC workload identity, OS keychain, `$VAULT_TOKEN`, or interactive TTY challenge).

## Execution flow

1. **Construction (plan).** Graph nodes declare required authority via `offer_reference_id`; saved in the signed graph.
2. **Resolution / bootstrap.** Resolve `authz.ProviderConfig` for the active profile and construct the `authz.Provider`
   broker router; **validate** — fail fast on any unknown or misconfigured broker.
3. **Preflight, in two places** (corrected 2026-10-21 to the passes the tree has). The graph-only check — every
   referenced offer is declared on some unit — joins `op.ValidateGraph` (`validate.go:49`, run at plan and load time
   beside `checkPromiseTypes` and the rest). The cross-check of **every** `offer_reference_id` against the resolved
   `authz.ProviderConfig.Offers` needs the resolved profile, so it joins `GraphExecutor.Run`'s preflight
   (`graph_executor.go:545-605`, after `NewRuntimeEnvironment`) and fails with `ReasonPreflightFailed`; any unresolved
   offer reference **refuses the run** before node 1 fires.
4. **Runtime node execution.** At the `authorize` node, the provider router dispatches to the offer's configured broker,
   acquiring the `Grant` (a `ProcessSpawn` runner session through the broker daemon, or an `IdentityAssumption`
   credential bundle) and returning the `*Lease` as the action's receipt, which the executor commits and pushes.
5. **Grant bridge & release.** For identity assumption, pass the `Grant` down typed edges into consumer input slots
   (§ The grant bridge, with its open question); consumers call `grant.Zero()` on completion. For the process case the
   session is the broker's and the consumer's command simply runs on it. Upon scope exit or rollback,
   `CompensateAuthorize` revokes the lease and records the audit event in the signed receipt.

## Failure routing

Three distinct failure classes at three distinct phases ensure no node ever runs unauthorized:

1. **Undefined offer / unconfigured broker → preflight refusal** (static / config error). Caught at preflight by
   cross-checking all graph `offer_reference_id` values against the profile-resolved `authz.ProviderConfig`. The
   graph *cannot start*, failing closed deterministically.
2. **Broker reachable, acquisition fails → node `flow.Failed` or `ErrPaused`** (runtime / dynamic).
   - If the offer specifies a `fallback_strategies` chain (e.g., `IdentityAssumption` → `InteractiveChallenge` when a
     local `sbx` or SSO session is expired), the stateful policy evaluator advances to the fallback strategy or pauses
     the unit (`ErrPaused`) for user interaction / `MandatedApproval`.
   - If all strategies are exhausted or denied, `Authorize` returns an error, triggering the unit's **`ErrorAction`**
     (`flow.Failed` floor) and halting the branch so downstream consumers never execute without a valid grant.
3. **Revocation / compensation failure → `flow.Degraded` / `FailedCompensation`.** Governed by the
   [compensation-failure contract](../plans/extract-starlark-from-op/phase-8/compensation-failure-contract.md); if
   `CompensateAuthorize` cannot revoke an active lease during unwind, the `RecoveryStack` marks the receipt outcome
   explicitly degraded rather than silently leaking authority.

## Audit

Every granted offer (`Authorize`) and lease termination (`CompensateAuthorize`) emits a structured audit record threaded
into the signed execution receipt and `RecoveryStack` trail — capturing the `offer_reference_id`, `broker_name`,
`strategy`, `grant_id` / JTI, timestamps, and revocation status without ever logging secret payloads (`MaskedVars`).

## Prior art & synthesis

This architecture synthesizes the **credential-broker pattern** (SPIFFE/SPIRE + Vault + cloud OIDC federation; see
*"Credential Broker Patterns for Secure CI/CD"*, arXiv 2504.14761), **workflow connection abstraction** (Airflow
Connections / GitHub Actions OIDC), **JIT PAM** (Teleport / Boundary / Aembit), and **OS privilege escalation** (Ansible
`become` / Polkit) into a single **compensable graph primitive**:

- **Unified capability model:** Host privilege escalation (`ProcessSpawn`), distributed token brokering
  (`IdentityAssumption`), and sandbox boundary initialization (`sbx`) share the same offer → broker → grant → lease
  lifecycle.
- **Pass-by-value dataflow:** Unlike external pipeline secret injectors that mutate global runner state, grants flow
  strictly along typed graph edges (`Grant`) with zero shared state across parallel branches.
- **First-class saga compensation:** Every acquired capability pairs with an `Lease` on the `RecoveryStack`
  so privileges and tokens are actively revoked on graph failure or rollback.

## Resolved design decisions (formerly open items)

1. **Provider & package naming — ruled 2026-10-21.** `authz.Provider` in `pkg/op/provider/authz`, paired with
   `authz.ProviderConfig`, `authz.Broker`, `authz.BrokerConfig`, `Grant`, and `Lease`; *authorization* the term.
2. **Router vs. global driver registry — settled.** Reconciled with [`3.2`](3.2-projected-provider-api.md) and
   [`configuration.md`](configuration.md): `authz.Provider` builds an internal router, itself a `Broker`, over
   interface-conformant `authz.Broker` instances configured in the profile-resolved `Brokers` config subtree. No global
   driver registration (`RegisterDriver`) or `op.BrokerRegistry` trait is used.
3. **Per-unit requirement representation — settled.** Units and `authorize` nodes reference abstract named offers
   (`offer_reference_id`) resolved at runtime against the active profile's `authz.ProviderConfig`; a command declares
   its account, and no `Mode` exists (ruled 2026-10-21).
4. **Unified realization surface — settled.** `ProcessSpawn` and `IdentityAssumption` share the `authz.Broker`
   acquisition/revocation surface and emit the unified `Grant` + `*Lease` pair, discriminated by `GrantKind`.
