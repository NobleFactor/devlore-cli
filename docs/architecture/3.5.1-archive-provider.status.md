## Document Discrepancies (design vs. current code)

- **Formats.** Only gzip-tar, plain tar, and zip extract; the design commits to the full tar family. The bzip2/xz/zstd
  paths are detection-complete and decompressor-absent.
- **Design signature is pre-taxonomy.** The design doc (§1) still says `Extract` "receives the archive as a
  `*file.Resource`" — since step 23 (2026-07-18) it receives a `*file.Regular` and returns `[]file.Entry`. The model is
  unchanged; the doc's type names need the taxonomy pass.

## Outstanding / open questions

Tracked in the design doc's §10:

1. Policy for tar symlinks, hardlinks, devices, and FIFOs — still silently skipped (`provider.go:425`). NEW since
   step 23: `file.SymbolicLink` and `file.Link` exist, so tar symlink entries could extract as tracked, compensable
   link mutations; this option did not exist when the design was drafted.
2. A total-extraction byte/entry cap beyond the per-entry `io.LimitReader`.
3. Adopting `github.com/cyphar/filepath-securejoin` (in-module, indirect) for symlink-aware containment.
4. Format-mismatch diagnostics when a decompressed payload is not a tar.
5. Whether a streaming zip reader is ever warranted.
