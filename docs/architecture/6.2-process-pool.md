## Thesis

**An execution host is a resource with an acquisition cost and a privilege identity, and devlore currently treats it
as neither.** Every command builds a fresh `*exec.Cmd`, so an acquisition that is expensive exactly once — a sudo
credential, a UAC consent dialog, a PowerShell module import — is paid again on every command, or not paid at all
because the code fails fast instead of asking.

Nothing here is novel, and the design is assembled from named prior art rather than invented (§2). Three ideas carry
it, and a fourth was ruled on 2026-10-21 (below): the host is a **runner daemon standing for an account**.

1. **Two kinds of persistence, deliberately separated.** *Persistent privilege* is an elevated parent that forks a
   fresh child per request — the credential survives, no execution state does. *Persistent interpreter state* is a
   live shell where variables and imported modules survive. They have opposite isolation properties and must not
   share a mechanism. §3.
2. **Identity, not instance.** Callers ask for a host *of a given identity*, never for a specific one. The pool
   decides whether that means starting one or handing back a running one, and **lazily to the point of never** — a
   run that does not take its elevated branch never elevates.
3. **Concurrency comes from multiplexing, not from more processes.** One host serves many in-flight requests when
   requests carry ids. This is what keeps a concurrent `gather` concurrent while an elevated identity is acquired
   exactly once.

## Ruled 2026-10-21: the runner stands for an account

The owner: "we provide an api for acquiring access to a command runner (a kind of sidecar) that runs under a specific
user account. It might be root. It might be non-root. there's always an account. we need to define this interface and
augment the pkg installers such that they get the command runner they need." Then: "I was thinking we had a pool of
command runner daemons; not necessarily a launchd daemon, though it might be"; "the command runner must be able to run
many commands under the user account that they stand for"; "I need a rock solid case using sh as my command runner";
and "The running processes must be able to do their thing and the command runner must be able to share its outputs and
narrations with the originator".

What that settles in this document:

- **The privilege axis of § 4 is an account.** Root is one account among others; the zero value is the caller's own;
  a runner under the caller's own account needs no grant. Elevation is the case where the account is root
  ([`6.1-authorization.md`](6.1-authorization.md)): an authorization that guarantees access to a runner standing for
  root.
- **There is no "whether".** `brew` does not say "never elevate"; it asks for a runner under the caller's account.
  `apt` asks for one under root. The manager backend declares the account its commands need, and `NeedsSudo()`,
  which nothing calls, becomes "which account". `runCommand(argv, sudo bool)` and `runWindowsCommand(command,
  elevated)` go.
- **The pool is a set of runner daemons**, one per account it stands for, the same binary for every account, and a
  runner **holds no shell**: every command is a fresh child, by argv or by `sh` on a static script file
  ([`6.3`](6.3-command-execution.md)). § 4.1 and § 4.2.
- **A child is never blocked by its originator.** The runner pumps each child's descriptors into a per-exec spool,
  and what the spool drains to — the broker ([`2.7`](2.7-control-plane.md)) or a direct caller — can be slow or absent
  without the child noticing. § 4.1.
- **Document 6's worker is this runner.** Its § Approach, § Interface Shape and § Remote Execution are absorbed or
  retired here, § 13.
- **The runner accommodates Windows.** The owner, later the same day: "I realize I've been talking as though we're all
  Unix. We need Windows support too and the command runner must accommodate." § 4.3 is the Windows runner, by the same
  protocol; where it needs a mechanism the tree has not verified, it says so.

## Ruled 2026-10-22: the runner is a logon, and the service manager makes it

The owner, 2026-10-22, on what running code as another account is for: "1 is all accessing network and operating
system resources. Grants to access these resources must be known to convey by the account I choose to use. 2 is all
about protecting network and operating system resources ... remote the test code selectively. 3 is all about account
claims on the network and operating system resources produced by a body of code. It is the user account that makes
these claims." On the mechanism: "It is the logon and the logon is to an account ... Sudo is a means to an end: a
logon." On a logon used to protect: "A good name for a logon that protects resources by identity is sandbox. It's a
specific kind of sandbox." On who makes the logons: "option 2. we do not want to be a key store. we need to rely on
the OS for that. option 3 is a good fallback on Unix. if the broker's service account can logon to the requested user
account, it will start a runner with sudo -u X."

What that settles in this document:

- **A runner is a logon, not a uid.** The grants of the first case, DPAPI and the Credential Manager, the macOS
  Keychain, a Kerberos ticket cache, an agent socket, live in a logon session, not in a uid; a process that is merely
  `setuid` to X is X to the filesystem and nobody to the Keychain. So the runner standing for an account is started by
  a real logon of that account, and § 4.1's `setuid` row is gone.
- **The service manager makes the logons.** launchd, systemd and the Service Control Manager exist to start a process
  as an account without anyone at a keyboard, under policy an administrator already owns. A runner is a service
  registered to run as its account, on every platform; the credential, where one exists, is the operating system's:
  a group managed service account or a virtual account on Windows, a keytab for a Kerberos identity. **Devlore holds
  no credential and is never a key store.** The broker ([`2.7`](2.7-control-plane.md)) is unprivileged; it connects
  to runners, it does not mint them. § 4.1, § 4.3, § 10.
- **`sudo -u <account>` is the Unix fallback**, not the mechanism: when no service is registered for an account and a
  sudoers rule lets the broker's service account start the runner binary as it, the broker does, and sudo's PAM
  session is the logon. It is audited and policed where administrators expect. Nothing like it exists on Windows.
  § 4.1.
- **An account is not a sandbox**, and the second case needs one. Running the test code as a throwaway account stops
  it writing the caller's files; it does not stop it reading anything world-readable, reaching the network or filling
  the disk. Containment is a second axis, the Job Object of § 4.3 on Windows and namespaces or seatbelt elsewhere,
  which the sandbox substrate of [`6.1`](6.1-authorization.md) owns; this document's runner supplies the identity.
- **The macOS login keychain is a GUI-session thing**, and the runner must say which kind it is. § 4.4.
- **The on-demand row is gone, and with it #528's question.** A service per account is the design on both platforms,
  not Windows's interim; whether a `LocalSystem` service can start a runner under an account with no session and no
  stored password no longer matters, because nothing does that. § 4.3, § Open 6.

## Ruled 2026-10-23 and 2026-10-24: the subgraph-executor, its identity, and what it writes where

On 2026-10-23 and 2026-10-24 the owner ruled on what a runner is when it runs a posted logon subgraph, how it is named, who elevates to it, and what it writes to each stream. This section states those rulings; the rest of the document is read against them.

- **The subgraph-executor.** A logon subgraph is the source of a three-tier request from the app, through the broker, to a subgraph-executor standing for an account. The executor is devlore running the subgraph through the graph executor, the way it runs any graph. It narrates through its own Narrator to its stderr, filtered by the flags the app passes with the request; it writes its result once, at the end, through its result pipeline to its stdout; it emits its events through OpenTelemetry (#1156).
- **The account belongs to the logon, and the broker elevates.** The app sends the subgraph and the account; the broker makes sure an executor is running as that account, starting one with its own privileges or reusing one, and every command inside runs as the executor's account. The broker therefore runs under an account with elevation privileges, and the app need not. Automatic elevation is recommended but not required; § Configuring the broker's account says how. This amends § Ruled 2026-10-22's unprivileged broker; devlore still holds no credential, and the service manager and `sudo -u` remain the means.
- **A processor is identified by its host and account.** The subgraph is the work, not the identity: one elevated executor runs many subgraphs, in parallel. The executor's version is a requirement the broker satisfies, matching the app's, not a path the app chooses. What names a processor is the account and the host, shown as `account@host`; with no host it is this machine. § 4's pool key takes the host.
- **Parallel subgraphs share one process.** So the executor keys every piece of per-run state, the run registry, each run's console and events streams, its recovery site, by run, never by process.
- **Standard error is narration, whole.** A child's stderr is pumped as bytes like its stdout: not split into lines, not limited in length, not repaired. § 4.1 item 3 is amended.
- **Events go through OpenTelemetry.** Devlore's own programs export to the endpoint in their environment; a program devlore runs takes part by its own configuration, assisted by the variables the command provider sets ([`2.8`](2.8-eventing-infrastructure.md)). Whether file descriptor 3 keeps a role is open (§ Open 9).

## 1. The problem, as the code stands

Three spawn paths exist today, and they do not agree on anything — not narration, not dry-run, not cancellation.

| Path | Site | Feeds | Context |
|---|---|---|---|
| Runtime runner | [`runtime_environment.go:726`](../../pkg/op/runtime_environment.go) — `re.runner()` builds a fresh `process.Runner` per call | `Capture` ([:390](../../pkg/op/runtime_environment.go)), `Emit` ([:428](../../pkg/op/runtime_environment.go)), `Run` ([:564](../../pkg/op/runtime_environment.go)); the `shell` and `powershell` providers | run-bound — cancellation kills the child |
| Platform shell | [`helpers_unix.go:56`](../../pkg/platform/helpers_unix.go) — `runShellCommand(command, sudo)`, a package var so tests can fake it | the `pkg` and `service` providers, through the manager backends | **`context.Background()`** with a fixed timeout |
| Windows managers | the winget leaves, driving their own path | Windows package operations | per-leaf |

Three defects follow, and the pool is the shape that resolves all three at once:

1. **`pkg/process` is not the single bridge it declares itself to be.** Its package doc states that *every* provider
   which shells out goes through `Runner`, so line-splitting, dry-run, cancellation and error wrapping live in one
   place. The platform path does none of that. This is the same class of finding that retired `internal/pwsh`,
   except this one is live and load-bearing.
2. **Run cancellation does not reach package installs.** `Runner`'s contract is that a canceled context kills the
   subprocess. `runShellCommand` uses `context.Background()`, so canceling a run leaves `apt-get install` running to
   completion. A pool that owns host lifetime owns cancellation with it.
3. **`sudo -n` fails rather than elevates.** The flag is deliberate — fail fast instead of prompting on a tty — but
   the consequence is that an operator without cached credentials gets a hard failure and no path forward. That is
   the standing TODO at [`helpers_unix.go:64`](../../pkg/platform/helpers_unix.go): *"centralize this. Route
   privileged execution through the ElevationOffer/Elevator — one credential-cached, policy-governed, audited sudo
   session — instead of every command inlining `sudo -n`."*

The *sometimes-privileged* character is already modeled: `NeedsSudo()` is true for systemd
([`linux_managers.go:147`](../../pkg/platform/linux_managers.go)), SysVinit
([:167](../../pkg/platform/linux_managers.go)) and the Windows Service Control Manager
([`windows_managers.go:36`](../../pkg/platform/windows_managers.go)), and false for a launchd **user** agent
([`darwin_managers.go:73`](../../pkg/platform/darwin_managers.go)). What is missing is somewhere for that answer to
go other than a boolean parameter.

## 2. Prior art — this is a solved problem

| Precedent | What to take |
|---|---|
| **Bazel persistent workers** | The closest analog. Long-lived workers keyed by a `WorkerKey` (mnemonic + startup flags + tool-input hash + sandboxing mode), speaking **length-delimited messages carrying a `request_id`**, so one *multiplex* worker serves concurrent requests. Also the cautionary tale: state leakage between requests produced nondeterministic builds, which is why worker sandboxing exists. |
| **PgBouncer pooling modes** | The vocabulary for the state question — *session*, *transaction*, *statement* pooling — and the honest rule that the aggressive modes **forbid** session state rather than pretending to reset it. |
| **`database/sql`** | The Go-idiomatic API: `MaxOpenConns` / `MaxIdleConns` / `ConnMaxIdleTime` / `ConnMaxLifetime`, acquisition that blocks at the cap, `sql.Conn` for pinned exclusive use, and the two driver hooks this design needs — `driver.SessionResetter.ResetSession` and `driver.Validator.IsValid`. |
| **PHP-FPM** (`pm = ondemand`, `pm.max_requests`) | Lazy allocation as a first-class mode, and **retirement** as the answer to state that cannot be fully reset: don't reset it, replace the host after N requests. Python's `ProcessPoolExecutor` carries the same idea as `maxtasksperchild`, plus an `initializer` hook — per-host setup paid once. |
| **SSH `ControlMaster`** | Authenticate once, run many **concurrent** channels over one connection. The direct precedent for "one credential acquisition, full concurrency," and already cited by [`6`](6-execution-topology.md) for remote execution. |
| **Nailgun / Gradle daemon** | Amortizing interpreter startup is a decades-old pattern with known failure modes (stale daemons, version skew). |

The tuning lesson these share: **the cap should match real concurrency, and queueing beats spawning.**

## 3. Two kinds of persistence

Merging these is the mistake this document was revised to remove.

**Persistent privilege.** An elevated parent that **forks a fresh child per request**. What survives is the
credential; no execution state does. Isolation is total — each request gets a new process — so there is no state
bleed, and concurrency is limited only by the parent's willingness to fork. This is what elevation needs, and it is
why an elevated identity capped at one host does **not** serialize the work it hosts.

**Persistent interpreter state.** A live shell in which variables, functions and imported modules survive across
requests. This is what the retired `internal/pwsh` wanted, for reasons that remain valid: PowerShell modules (Az,
ActiveDirectory) authenticate on import, COM/.NET objects (WMI, Registry, IIS) are expensive to instantiate, and DSC
requires compile→test→apply in one session. It is also the only case with a state-bleed problem.

A pool serving both must know which it is providing. They differ in isolation, in concurrency, and in whether a
reset is even possible.

## 4. Host identity — the pool key

Two requests share a host when they share an identity, modeled on Bazel's `WorkerKey`:

- **Interpreter** — `bash`, `pwsh`, or the worker binary.
- **Host** (added 2026-10-24) — the machine the processor runs on; none is this machine. A remote processor is an address whose host is not this one, so the local and remote cases are one rule.
- **Account** (revised 2026-10-21; was *privilege*, binary) — the user account the host runs as: root, the caller's
  own, a service account. The zero value is the caller's own. It is the *outcome* of an authorization, not the
  request: two units arriving at the same account by different routes still share. How the account is named — user
  name, uid, or a role such as `root` and `caller` — is open (§ Open, 8).
- **Pooling mode** — §5. A session-mode acquisition is never interchangeable with a statement-mode one.
- **Session** — the owning `RuntimeEnvironment`. The pool is a **session service**, never a process singleton,
  following the `Invoker` precedent: two graphs running concurrently in one process share nothing.

Deliberately **not** in the key: working directory and environment variables. They travel with the request, because
folding them into the identity fragments the pool toward one host per call site and defeats it.

### 4.1 The runner daemon

A runner is **one long-lived process standing for one account**, the same binary whatever the account, with its
effective uid set to that account. It is the persistent thing; the commands it runs are not.

| Account | How the runner comes to exist | Its socket |
|---|---|---|
| root | a system daemon: launchd, a systemd unit, a Windows service | owned by root, mode `0600`, under `/var/run/devlore/` (illustrative) |
| the caller's own | a user agent: a launchd agent, `systemd --user`, a logon-triggered task on Windows | under `$XDG_RUNTIME_DIR/devlore/` |
| a service account | a **service registered to run as the account**, started by the service manager, which makes the logon (ruled 2026-10-22); on Unix, when no service is registered and a sudoers rule allows it, the broker starts the runner binary with `sudo -u <account>`, and sudo's PAM session is the logon | owned by the account, mode `0600`; under the broker's directory when sudo started it |

"Not necessarily a launchd daemon, though it might be": the first and third rows are, the second is an agent, the sudo
fallback is neither, and the protocol does not know the difference. No row forks and `setuid`s: that made a uid, not a
logon (§ Ruled 2026-10-22).

**What a runner does, per exec.** It accepts a request `{rid, argv | script, env, cwd, stdin}` on a multiplexed
connection — many requests in flight, each with its id (§ 6) — and for each:

1. **forks a fresh child** that inherits the runner's account, so no command carries `sudo` and nothing escalates
   inside the child; tier 1 is `execve` of the argv, no interpreter at all; tier 2 writes the script body to a file in
   the runner's scratch root (mode `0600`) and runs `sh file "$1" "$2"`, values as arguments, never interpolated
   ([`6.3`](6.3-command-execution.md)); **stdin is an attribute of the request** (a byte string, or `auto_confirm`,
   which is what `pkg/platform`'s `y\n` stream is today), closing 6.3's open question 3;
2. **pumps the child's stdout and stderr unconditionally** into two per-exec **spools** — memory first, a file in the
   scratch root when memory fills, never dropped; a full disk fails the exec with a named error — so a pipe nobody is
   reading can never fill and block the child. The spools drain to the consumer as fast as it accepts;
3. **frames** what it drains: `{rid, channel, payload}`, `channel` one of `output` (stdout, bytes, a frame per filled
   chunk or timer tick, no decoding), `narration` (stderr, bytes, exactly as `output` carries stdout: no line splitting, no length limit, no repair; amended 2026-10-23, since filtering is the program's business and nothing downstream reads its narration), and `control` (the exit status, never inferred from a stream closing). Events are not a frame channel since 2026-10-24: devlore's programs export them through OpenTelemetry; whether fd 3 survives as a local carrier is § Open 9;
4. **cancels** on `{rid, cancel}` with `SIGTERM` then `SIGKILL` to that one child, and reports the exit as a control
   frame.

Between requests it holds **nothing**: no working directory, no variables, no imported modules. That is § 3's
"persistent privilege, not persistent interpreter state" and § 5's statement mode, made structural: there is no state
to forbid because there is no shell to hold it. Session mode survives only for the runspace host (§ 8), where the
interpreter *is* the unit of execution.

**Who acquires.** The broker ([`2.7`](2.7-control-plane.md) § The runner selector) maps an account to a runner session
and holds it for the run; a caller may also go **direct** to the runner standing for its own account, the same frames,
no policy. On the broker hop the exec's frame stream is the response body of the broker's `POST /exec` to the runner,
one HTTP/2 stream per exec; on a socketpair it is the same frames, length-prefixed, without the facade. The manager
backends of `pkg/platform` reach the runner through the provider that owns them, which declares the account, so § Open
question 2 of the previous revision — "they call a package var" — is closed by the ruling: the caller owns the session,
the leaf receives the runner.

### 4.2 The case for sh

"A rock solid case using sh as my command runner." The case is that **sh is never the runner**; it is the interpreter
of one static script file for one command, and it exits with the command.

- **Present everywhere.** POSIX `sh` is on every Linux and macOS host, and `dash`, `bash` and `zsh` in sh mode all run
  the same static body. `pwsh` is not (§ 8); nor need it be for the Unix path.
- **Nothing to quote.** The body is static and values arrive as `"$1" "$2"`; the two dialects' quoting rules
  ([`6.3`](6.3-command-execution.md) § 1) never apply, because no value is ever inside the body.
- **No state between commands.** One child per command, so `cd`, exported variables and sourced files die with it;
  statement mode is a property of the shape, not a promise to clean up.
- **Nothing to escalate inside.** The child is the runner's account by fork. A script that says `sudo` is a script
  that asked the wrong runner.
- **A kill that lands.** One command is one process tree under one child; cancelling the rid signals exactly that.
- **Tier 1 needs no sh at all,** and [`6.3`](6.3-command-execution.md) showed all seventy platform commands fit tier 1.

### 4.3 Windows: the same runner, by the platform's means

The protocol, the frames, the spools and the per-exec child are the same on Windows. What differs is how a runner
standing for an account comes to exist, how a child is created under it, and what cancel means. Each row names its
mechanism and whether the tree has verified it.

| Concern | Unix | Windows | Verified |
|---|---|---|---|
| the runner for the root analogue | a system daemon, launchd or systemd | a **Windows service** registered to run as `LocalSystem` (or a service account in Administrators); the Service Control Manager starts it, as launchd does | the service model is standard; devlore has no service yet |
| the runner for a service account | a service registered to run as the account (launchd, systemd); `sudo -u` as the fallback | a **service per account**, registered at install to run as that account — a virtual account (`NT SERVICE\devlore-runner-<name>`) or a group managed service account, so no password is stored anywhere; the SCM makes the logon. This is the design, not the interim (ruled 2026-10-22): there is no on-demand row on either platform, so the token path [#528](https://github.com/NobleFactor/devlore-cli/issues/528) was reframed to verify is not needed | standard |
| the runner for the caller's own account | a user agent, `launchd` or `systemd --user` | a process started at the user's logon (a logon-triggered scheduled task), standing for that user; not a service | standard |
| the socket | a Unix domain socket, mode `0600`, `SO_PEERCRED` | a **named pipe** `\\.\pipe\devlore\runner-<account>` with a DACL granting connect to the broker's account (and the user, for the direct path); the client's identity from the pipe's client token (`ImpersonateNamedPipeClient` to read it, then revert), the analogue of the peer uid | standard |
| the account's name | user name, uid, or role (§ Open 8) | the **SID**; `caller` resolves to the pipe client's user SID | — |
| tier 1, argv | `execve` of the vector | `CreateProcess` takes one command line and the child's C runtime re-parses it; the runner encodes the argv by the CRT's rules, which is what Go's `os/exec` does (`syscall.EscapeArg`); no shell, nothing quoted by hand ([`6.3`](6.3-command-execution.md) § 2) | standard |
| tier 2, the script file | `sh file "$1" "$2"` | `pwsh -NoProfile -NonInteractive -ExecutionPolicy Bypass -File r42.ps1 arg1 arg2`, the body static with `param()` ([`6.3`](6.3-command-execution.md) § 3.3); Windows PowerShell 5.1 when `pwsh` is absent (6.3's open question 5) | standard |
| the runspace host (§ 8) | the same | the same: a PowerShell-side host owning a `RunspacePool`; the only place session mode exists | designed |
| stdout, stderr | anonymous pipes | anonymous pipes, inherited handles | standard |
| the third channel (fd 3) | a third inherited descriptor | an inherited pipe **handle** passed through `STARTUPINFOEX`'s attribute list, its value in an environment variable the devlore-aware child reads, since Windows inherits handles by explicit list, not by number | standard, untried here |
| the scratch root for tier 2 files | mode `0600` under the runner's scratch root | a DACL for the runner's account only (`applyMode`'s DACL, [`6.3`](6.3-command-execution.md) § 3.2) | exists |
| cancel | `SIGTERM`, then `SIGKILL` to one child | the child is created in a **Job Object** with `KILL_ON_JOB_CLOSE`, so cancel kills the whole tree; a `CTRL_BREAK` first where the child has a console | standard |
| the UAC dialog | — | **never from a service**; it exists only in the desktop interim row of § 10 | — |

Every row is standard or exists. The token path for on-demand spawn, which [#528](https://github.com/NobleFactor/devlore-cli/issues/528)
was reframed to verify on 2026-10-21, dropped out the next day with the on-demand row itself: a service per account is
the design, and no service starts a runner under another account. #528 is the owner's to close on reading this. The
JEA row of § 10 stays only as the alternative for a machine where registering a service per account is refused.

### 4.4 macOS: two kinds of runner, and the keychain

The owner, 2026-10-22: "The macOS keychain is a bitch that way. You'd like to keep the password you need in the
keychain, but the keychain is locked."

A macOS account's **login keychain is unlocked only inside a GUI session**. A service logon gives the account's uid,
its files and its Kerberos identity, and not its keychain. So there are two kinds of macOS runner, and the runner
declares which it is, and the account's offer ([`6.1`](6.1-authorization.md)) says which it conveys:

| Runner | Made by | Has the login keychain | For |
|---|---|---|---|
| a **LaunchAgent** in `gui/<uid>` | launchd, inside the account's logged-in session | yes | a human account, on a machine that is logged in, which on a headless Mac means auto-login |
| a **LaunchDaemon** with `UserName` | launchd, at boot, no session | **never** | a service account |

What keeps its secret in the login keychain, and therefore fails on a daemon runner: `gh`, whose token is there by
default; `git push` over HTTPS through the osxkeychain credential helper; `ssh` with a passphrased key the keychain
agent holds; `codesign` and `notarytool`, which in a GUI session raise a dialog nobody sees and headless return
`errSecInteractionNotAllowed`, or hang; the Azure and AWS CLIs and Docker Desktop's credential helper. Media-Server
does not show this today because it auto-logs in; it will show the first time a runner for a second account runs one
of these, which is iteration 3.

The rule:

1. **A keychain-dependent command on a daemon runner fails at authorization**, as a named failure with a sentence,
   never a dialog and never a hang. The offer says the runner conveys no keychain; the unit's `ErrorAction` handles
   the failure like any other ([`6.1`](6.1-authorization.md) § Failure routing).
2. **A service account's secrets are files and tokens, not a keychain**: `GH_TOKEN`, a file credential store for git,
   ssh keys without passphrases, each mode `0600` under the account's home. A keychain unlocked from a stored
   password is a `0600` file with extra steps and the appearance of more; it is not used.
3. **Signing, the one case that insists on a keychain, uses a scratch one**: the runner creates a temporary keychain
   per run with a random password held only in memory, imports the identity from wherever secrets come from, signs,
   and deletes the keychain. The keychain is a workspace, never a store.
4. **Iteration 3 carries the acceptance test**, on a Mac: a daemon runner for a fresh service account runs
   `security find-generic-password` and `gh auth status`, and what comes back is the sentence of rule 1.

## 5. Pooling modes

Adopted from PgBouncer, whose taxonomy answers what three home-grown options could not:

| Mode | Host returned to the pool | State guarantee | For |
|---|---|---|---|
| **Statement** | after every request | none — session state is **forbidden**, not reset | the default; `shell.exec`, `pkg.install`, `service.start` |
| **Session** | when the acquirer releases it | full — the acquirer owns the host exclusively | Az login → deploy → verify; DSC compile→test→apply |
| **Transaction** | at a declared boundary | state survives within the bracket only | reserved; no consumer today |

The rule that makes this honest is PgBouncer's: **statement mode does not promise a reset — it promises that state
was never allowed.** Where an interpreter cannot enforce that (PowerShell module imports cannot be un-imported), the
answer is retirement, not reset: replace the host after N requests, as PHP-FPM does. `IsValid` decides whether a
returned host is fit to reuse; `ResetSession` does what cleanup is possible; `max_requests` bounds what neither can.

## 6. Concurrency

**Multiplexing, not more processes.** Each request carries an id, and a host may have several in flight. This is
Bazel's multiplex worker and SSH's channel model, and it is what keeps a concurrent `gather` concurrent:

- **Unelevated, statement mode** — per-identity cap above one; requests spread across hosts *and* multiplex within
  them.
- **An account other than the caller's** (root, a service account) — cap of **one runner**, with many concurrent
  requests multiplexed over it. The one runner forks a child per request (§3, §4.1), so concurrency is preserved while
  the authorization is granted exactly once. Raising the cap would repeat the grant for no throughput gain.
- **Session mode** — one acquirer, no multiplexing. That is the point of the mode.

Requests beyond the caps queue rather than spawn, and queueing is narrated: a gather that waits on an elevated
identity should say so rather than merely run slowly.

## 7. Framing

Messages carrying a **request id**: `{rid, argv | script, env, cwd, stdin}` in, and frames `{rid, channel, payload}` out
with `channel` one of `output`, `narration`, `control`, `narration` carrying stderr's bytes (§ 4.1; amended 2026-10-23 and 2026-10-24: no `event` channel, since events go through OpenTelemetry; revised 2026-10-21 from `(id, stdout, stderr,
exit_code)` so that output and narration stream as they happen rather than arrive at exit). On the broker hop the
frames are the response body of one HTTP/2 stream per exec; on a socketpair they are length-prefixed.
[`6`](6-execution-topology.md) proposed ndjson; **request ids are the addition that matters**, because without them a
host can only serve one request at a time and §6 collapses.

**Do not adopt the marker protocol from the prior art.** The retired `internal/pwsh` framed output by writing a
sentinel line and reading until it appeared, which breaks the moment a command's own output begins with that
sentinel.

## 8. Host kind is chosen by the interpreter, not the platform

The pool has **two host kinds**, and which one serves a request is decided by the interpreter in its identity (§4) —
never by the operating system it happens to be running on:

| Host kind | Unit of execution | Interpreters | Isolation |
|---|---|---|---|
| **Process-per-request** | an OS process | `bash`, and the elevated forking parent (§3) | by construction — every request is a new process |
| **Runspace pool** | a runspace: a thread-level context with its own session state | `pwsh`, on **every** platform | per-runspace; a fresh runspace is statement mode, a pinned one is session mode |

A POSIX shell's unit of execution is a **process**. PowerShell's is a **runspace**, and `pwsh` already ships the pool
this document is designing: `RunspacePool`, with a min/max and asynchronous `BeginInvoke`. Pooling `pwsh`
*processes* would ignore the runtime's own answer and pay process cost for what it does with threads.

**This is a property of PowerShell, not of Windows.** `pwsh` is cross-platform, so `powershell.exec` on Linux or
macOS gets the runspace host, session mode, amortized module imports and object fidelity exactly as Windows does.
The platform selects the *elevation* mechanism (§10); the interpreter selects the *host kind*.

**The shape this implies.** The PowerShell host is not a Go-spawned command loop but a **PowerShell-side host script**
that owns a `RunspacePool`, reads framed requests, dispatches each to a runspace, and writes framed responses. Go
speaks the protocol; PowerShell owns the execution. That yields, natively and without invention:

- **Concurrency inside one process** — N runspaces on threads, not N `pwsh` processes.
- **Both pooling modes for free** — a fresh runspace per request *is* statement mode; a runspace pinned to an
  acquirer *is* session mode. §5 maps onto the platform primitive exactly.
- **Module import amortized** — the `initializer` idea, as a runspace-pool `InitialSessionState`.

**The object boundary is the real design question.** PowerShell pipelines carry live .NET objects; `pwsh -Command`
flattens them to formatted text, which is lossy and unstable — today's `powershell.exec` returns `Stdout string`, so
every structured result is already being destroyed at the boundary. Crossing into Go requires a serialization
choice: `ConvertTo-Json` (readable, depth-limited, lossy for types) or CLIXML via `PSSerializer` (PowerShell
remoting's own format, higher fidelity, produces property-bag "deserialized" objects that lose methods). Neither is
free, and choosing is a prerequisite to any of this.

**PSSession may also answer elevation on Windows, which nothing else does.** PowerShell's session configurations —
JEA endpoints registered with `RunAsVirtualAccount` — let an unprivileged caller connect to an endpoint that
executes under a privileged virtual account. Because it is service-hosted rather than desktop-elevated, it plausibly
works **headless**, where UAC categorically cannot. It moves the one-time elevated act to endpoint registration
(install time), which is the right place for it. PowerShell 7 also carries PSSession over SSH on Linux and macOS,
tying into [`6`](6-execution-topology.md)'s multiplexing section.

This is the most promising unverified claim in this document and is called out as such: it needs a spike on a real
Windows host before anything is built on it (open question 6).

### Why `pwsh` is not promoted to the universal host

Since `pwsh` runs everywhere and brings runspaces with it, the obvious question is whether it should simply *be* the
host on Unix too, collapsing the two host kinds into one. **It should not**, and the reason is specific rather than
sentimental:

**PowerShell's object model exists for cmdlets, and there are no cmdlets on the Unix path.** The work devlore does
there is `apt-get install -y`, `systemctl start`, `brew install`, `port -N install` — external POSIX programs.
Invoking them from `pwsh` returns exactly what invoking them from `bash` returns: text on stdout and an exit code.
The single largest advantage would be paid for and not received.

What remains does not carry the decision:

- **Concurrency is not a reason.** §3's elevated parent forking per request already gives one host and N concurrent
  requests without a second runtime.
- **The dependency is severe.** `sh`/`bash` is present on every Linux and macOS host; `pwsh` must be installed from
  Microsoft's repository or a package manager. Today the hard `pwsh` requirement is scoped to one provider a user
  opts into; making it the universal host makes it mandatory for every run — including the bootstrapping paradox of
  needing `pwsh` present to run the tool that installs it.
- **Cost.** Cold start is hundreds of milliseconds against `bash`'s few, and roughly 60–100 MB resident against ~3 MB.
  Pooling amortizes the former only when the pool is warm, which a one-shot CLI invocation may never be.
- **It would not remove `bash` anyway.** `shell.exec` bodies are POSIX text with POSIX quoting, so a POSIX shell is
  still required; `pwsh`-as-universal-host adds a layer rather than replacing one.
- **Native-command argument passing differs enough to bite** — the reason PowerShell carries `--%` and later
  `$PSNativeCommandArgumentPassing`. Existing manifests and `.star` snippets assume POSIX rules.

So `pwsh` is a first-class host kind wherever `pwsh` is the interpreter asked for, and never the default.

## 9. Lazy allocation and lifetime

No host starts until a request needs one of that identity. A dry run allocates **nothing** — `Runner` already
narrates without executing, so the pool's acquire returns a narrating stub and a dry run of an elevated graph never
prompts for credentials. Today's platform path does not honor dry-run at all, which this fixes as a side effect.

Revised 2026-10-21: a runner daemon **outlives runs** — a system daemon or a user agent is always there, and an
on-demand runner lives until idle. What is per-run is the **session** the broker holds on it (§ 4.1, "who acquires"),
and that session must **outlive the forward pass**: compensation runs after failure, and an undo that needs root must
not be what re-acquires a grant. The session is released after compensation, not after the last forward unit. The
previous revision's "a session service, never a process singleton" now describes the broker's session on the runner,
not the runner; one runner per account per machine is a singleton by design, and two concurrent runs share it by
multiplexing while sharing no state (§ 3).

## 10. Platform divergence — elevation only

Host kind is the interpreter's business (§8). What the **platform** decides is how an elevated identity is acquired:

| Platform | How the runner for root exists | IPC | Elevation cost |
|---|---|---|---|
| Linux / macOS | a system daemon (launchd, systemd) registered once under `sudo`, one service per account the machine offers; `sudo -u` from the broker's service account under a sudoers rule for an account with no service (ruled 2026-10-22, § 4.1) | Unix domain socket | none per run; one registration per account |
| Linux / macOS, interim | `op.InProcessBroker` (#1130): a root exec is the caller's process forking `sudo -n argv`, the one place the word appears in `pkg`; the caller's own account is the same broker's direct path, kept past this row | pipe | one prompt per run, or a cached credential |
| Windows (desktop) | `runas` / ShellExecute with the `runas` verb | **named pipe** — the native IPC | one UAC dialog; UAC is per-process and **cannot be cached**, so pooling is the only mechanism that yields one dialog |
| Windows (headless), revised 2026-10-22 | a **Windows service per account**, registered at install (§ 4.3); `LocalSystem` for the root analogue; the SCM makes each logon and no token path is needed, since nothing spawns on demand | named pipe | none per run; one registration per account |
| Windows (headless), alternative | JEA session configuration, `RunAsVirtualAccount` — §8, unverified | PowerShell remoting | one-time elevated registration at install; none per run |

The rows are orthogonal to host kind: a runspace-pool host on Linux is acquired unelevated in-process and elevated
through `sudo` exactly as a `bash` host is, and the JEA row is the one place the two intersect — because there the
elevation mechanism *is* a PowerShell session.

A service per account is headless Windows's elevation mechanism (ruled 2026-10-22); JEA is the alternative where
registering one is refused. On either, an acquire that cannot be served fails as a named policy failure routed
through the failure contract — never a dialog nobody can see. The same sentence covers the macOS keychain, § 4.4.

## 11. Relationship to elevation

The pool is the **mechanism**; [`6.1`](6.1-authorization.md) owns the **policy** and the provider:

- **`ProcessSpawn`** becomes "acquire a session on the runner standing for the account" (revised 2026-10-21; the
  strategy's grant *is* the session, and its lease *is* the session: revoking it releases the runner, and there is no
  sudo timestamp to revoke because the runner holds the privilege, not the caller's shell). The strategy needs no
  privileged-worker design of its own — the worker *is* a runner (§ 4.1, § 13).
- **`IdentityAssumption`** does not touch the pool: it mints a token and bridges it down an edge.
- **`InteractiveChallenge`** / **`MandatedApproval`** ride pause/resume, so acquire must tolerate suspending and
  resuming — including across a process restart, where nothing pooled survives.

## 12. Hermeticity

[`2.4-hermeticity-guarantees.md`](2.4-hermeticity-guarantees.md) is the constraint a pool most obviously strains: a
reused host is a channel between units that the graph does not model as an edge. §5 is the answer — statement mode
forbids the state rather than promising to clean it, and session mode makes the sharing explicit and exclusive — but
`2.4` must say so too, and today it does not.

## 13. Absorbed from document 6 (2026-10-21)

[`6-execution-topology.md`](6-execution-topology.md) designed the mechanism this document now owns, before the pool and
before the ruling. Three of its sections are absorbed or retired here, and it keeps the problem, the policy triplet and
the topology.

- **§ Approach — the privileged child process.** "The worker is a generic command executor … file operations that need
  root (writing to `/etc`) go through the same channel." The worker is the runner of § 4.1. File operations under root
  become **commands** on the runner standing for root; how writ's System scope reaches it — `devlore run --graph` as
  one command on the root runner, which keeps the file provider's semantics, or each file operation as a command — is
  [`2.7`](2.7-control-plane.md) § Open question 1, the broker's size.
- **§ Interface Shape — `{Start, Exec, WriteFile, Stop}`.** Retired. `Start` and `Stop` are the runner's lifetime (§
  4.1's table); `Exec` is the request; `WriteFile` is a command.
- **§ Remote Execution — `Executor{Upload, Execute(cmd string, elevated bool), Download}` over SSH.** Retired onto
  [`2.7`](2.7-control-plane.md)'s wire: the string loses to [`6.3`](6.3-command-execution.md)'s argv rule, the boolean
  to the account, the SSH transfer to the same API over TLS. A remote runner is a runner whose identity carries a host,
  reached through that host's broker (§ Open, 11).

## Open questions

1. **Serialization at the PowerShell boundary** — JSON with a depth limit, or CLIXML with remoting fidelity? Gates
   §8 entirely, and is worth answering even if the runspace host is deferred, because `powershell.exec` is lossy
   today.
2. **Who acquires? — closed 2026-10-21** by the ruling: the provider that owns a manager backend declares the account
   and holds the runner session; the backend receives the runner. "Caller owns, leaf receives," as the filesystem
   roots answered it ([#405 phase 2b](../plans/windows-native-permissions.md)).
3. **Retirement thresholds** — what N, and per interpreter or global?
4. **Does the pool subsume `runShellCommand`'s knobs?** It carries `DEBIAN_FRONTEND=noninteractive` and a stdin of
   repeated `y\n` — package-manager-specific behavior a general pool should not know, but which has to live
   somewhere.
5. **Worker binary — half closed 2026-10-21:** the worker is the runner daemon, the same binary for every account.
   Whether that binary is `devlore` behind a flag or its own is [`2.7`](2.7-control-plane.md) § Open question 2. The
   PowerShell host is a *script*, not this binary.
6. **Spike the Windows token path — dissolved 2026-10-22.** A service per account is the design and nothing spawns on
   demand, so the question #528 was reframed to on 2026-10-21 has no subject (§ 4.3). #528 is the owner's to close.
7. **Pause/resume across restart** — a resumed run re-acquires its session; with a runner daemon that is a reconnect,
   not a second credential prompt, unless the interim `sudo` row of § 10 is in use. Whether a re-acquired session may
   resume a child that outlived the broker is unanswered.
8. **Naming the account** — user name, uid, or a role (`root`, `caller`, a service account's name). A role keeps the
   graph environment-agnostic, which the three-way split of [`6.1-authorization.md`](6.1-authorization.md) requires;
   Windows wants a SID.
9. **fd 3 — ruled 2026-10-22; reopened 2026-10-24.** Ruled 2026-10-22, events from a devlore-aware child go to fd 3 and narration to stderr, with nothing sniffed. Since 2026-10-24 every devlore program exports its events through OpenTelemetry to the endpoint in its environment, so fd 3 has no traffic of its own: either it is retired, or it becomes the local carrier of a child's OTLP to the broker, for a child that cannot reach the Collector. Recommended: retire it. For ruling.
10. **Accounts that are neither root nor the caller — answered 2026-10-22.** Supported from the first cut by
    registration: a service per account, or the sudo fallback, § 4.1. There is no on-demand row to defer them with.
11. **Remote runners — answered 2026-10-24.** A processor's identity carries a host (§ 4); the broker reaches a remote one through SSH, shipping a bundle that ensures the executor is present, the subgraph is present, and it runs under the account's credentials, with no broker on the far machine ([`2.7`](2.7-control-plane.md) § The remote leg). The bundle's contents and installation are #1160.
12. **Where the runner's types live** — `pkg/process` (it runs), `pkg/op` (the executor manages its session), or the
    `authz` package (a grant gives access to it). The dependency direction decides: `authz` grants, the broker
    consumes grants, `process` runs. Narrowed 2026-10-22: `authz` is strictly token acquisition
    ([`6.1`](6.1-authorization.md) § Ruled 2026-10-22), so the runner's types are not its.
13. **A unit's account is fixed when the unit is planned — settled by construction 2026-10-22.** Ownership, audit
    entries and a daemon's identity are fixed at the moment of production and cannot be reassigned afterward, so
    "remote when the first protected call fails" was never available. `plan.logon` takes its account as an argument
    ([`2.3`](2.3-orchestration-primitives.md) § Ruled 2026-10-22), which fixes it at plan time.

14. **The SSH client and the remote events channel** ([`2.7`](2.7-control-plane.md) § Open). Go's SSH package carries a channel of our own for OpenTelemetry beside the session, on every platform, and reads a host's configuration from `ssh -G`; the OpenSSH client honours the whole configuration but multiplexes nowhere on Windows, where a remote port forward to the Collector would carry the events instead. For ruling. Whether one connection carries many sessions, and whether the far side runs an executor per session or a daemon, are [`2.7`](2.7-control-plane.md) § Open 21 and 22.

## Configuring the broker's account

Ruled 2026-10-24: the broker runs under an account with elevation privileges, and the app need not. Automatic elevation is recommended but not required. How to configure that account, per platform (#1167):

- **Linux and macOS.** A sudoers rule for the broker's account, in a file under `/etc/sudoers.d/`, allowing it to run the executor binary as the accounts it may stand for and nothing else. With `NOPASSWD` the elevation is automatic; without it, sudo asks, and a run with no terminal fails by name rather than waiting.
- **Windows.** A service account in the Administrators group, or `LocalSystem` for the root analogue; the Service Control Manager starts the broker under it.
- **In iteration 1** the in-process broker runs as the app's user, so the app's user is the account configured, until the broker leaves the app's process in iteration 2.
