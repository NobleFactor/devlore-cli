How resource types announce themselves and how typed resources are constructed from raw values — the resource half
of the registration model whose provider half is [3.1 Provider Loading](3.1-provider-loading.md).

See also: [4-resource-management.md](4-resource-management.md) ·

## 1. The model — one registry, generated announcements

Every resource type announces itself to the **receiver registry** at init, from a generated file (one per resource
type — e.g. `pkg/op/provider/file/gen/regular.gen.go`, `directory.gen.go`, `symbolic_link.gen.go`):

```go
// Code generated by go.render; DO NOT EDIT.
func init() {
	op.AnnounceResource(
		reflect.TypeFor[provider.Regular](),
		func(runtimeEnvironment *op.RuntimeEnvironment, identity any) (op.Resource, error) {
			return provider.DiscoverRegular(runtimeEnvironment, identity)
		},
		map[string][]string{ /* starlark parameter names per Go method */ },
	)
}
```

`AnnounceResource(resourceType, construct, methodParameters, sourceTypes...)` (`pkg/op/receiver_registry.go`)
registers a `RoleResource` receiver type — resources are data types, never actions or modules. The pieces:

1. **The constructor** — `ResourceConstructor`: coerces a raw identity value into the typed resource, **with the
   runtime environment in hand** (construction may consult the root, catalog, or platform). Hand-written by the
   provider developer (`DiscoverRegular`, `DiscoverResource`, …); the generated file only wires it.
2. **Method parameters** — the announced starlark surface for attribute access on the resource
   (`Equal`, `CanConvertFrom`, `ConvertFrom`, …).
3. **Source types** (optional, variadic) — Go types this resource is constructed *from* (§3).

Announcement is **eager but cheap** (a registry entry); construction happens on demand at the registry's lookup
paths. There is no per-type lazy `Init` step — the pre-`op` descriptor model this document once described was
superseded by the single receiver registry.

**The announcement enforces the shape** ([#646](https://github.com/NobleFactor/devlore-cli/issues/646), 2026-09-08).
`AnnounceResource` runs `CheckSealedShape` and refuses any type that is not a sealed interface over an unexported
struct (§5), naming the type and the rule it broke. A non-conforming provider therefore fails to start rather than
waiting for a review, and `pkg/op/inventory`'s boot-discipline suite reads the same rule back over every announced
type. Only this announcement is held to the shape: `AnnounceProvider` and `AnnounceType` (a provider; a plain data
type such as a result struct) never consult it.

## 2. Construction paths

A registered constructor is reached three ways:

1. **Target-driven conversion** — a slot names the resource type and the value is a plain identity (a string path,
   a URI): the conversion cascade resolves the type's constructor and builds the typed resource
   ([2.1](2.1-typed-slots.md) §Plan-Time Conversion; the catalog behavior matrix governs what happens on the claim
   — [4](4-resource-management.md) §3).
2. **Source-driven construction** — the *value's own Go type* selects the resource (§3): the planner asks
   `ReceiverRegistry().ConstructorForSource(reflect.TypeOf(value))` (`pkg/op/planner.go`) before its addressing
   switch.
3. **Rehydration** — a serialized resource's URI fragment names its canonical Go type id;
   `ResourceConstructorByTypeID` resolves the constructor so the load path reconstructs the concrete type
   ([5.2](5.2-recovery-serialization.md)).

## 3. Source-type declaration (typed constructors)

The default constructor takes `any` — a poor man's union, since Go has no sum type for a *value* parameter. An
`any` constructor is **target-driven only**: `op.Convert` reaches it when a slot already names the resource type
(e.g. a string URI coerced to a `*function.Resource`).

A resource born from a specific Go value — notably a Starlark builtin like `*starlark.Function` — declares that
**source type** by constraining the constructor with a type set, the one form of union Go *does* have (in
constraint position) and the only one codegen can read off a signature:

```go
func NewResource[T *starlark.Function | string](
    env *op.RuntimeEnvironment, unit op.ExecutableUnit, identity T,
) (*Resource, error)
```

Codegen reads the type-set members — `goast` surfaces the type-parameter constraint — and keeps only **Starlark
builtins** (an allowlist: the exported `go.starlark.net/starlark` data types plus `starlark.Value`), registering
`byType[sourceType] = the receiver type` for each through `AnnounceResource`'s source-types argument, reusing the
existing type map (**no new registry**). A member outside the allowlist — a Go primitive like the URI `string` — is
**not** keyed and stays target-driven. So `*starlark.Function → function.Resource` becomes a source key while
`string` does not.

The read side is `op.ReceiverRegistry().ConstructorForSource(reflect.TypeOf(value))`, called by the planner: when
an immediate value is a Go type with a registered source constructor, the planner builds the resource before its
addressing switch — naming only `op` and `reflect`, never the provider. This is how a Starlark function reaches its
content-addressable `function.Resource` without `op` or `starlarkbridge` depending on `function`.

A resource may pair a **typed source constructor** (the declaration, e.g. `NewResource`) with an **`any` announced
constructor** (the target-driven path, e.g. `DiscoverResource`). The generic shell stays thin — it erases to `any`
into a shared unexported builder — so the only monomorphized code is the constructor's few lines.

## 4. Callables — where the old extraction model went

The pre-`op` callable-extraction pipeline (`CallableResource`, `extractCallable`, `initCallableSlots`,
`buildCallableFunc`) no longer exists. A `*starlark.Function` argument becomes a content-addressed
**`function.Resource`** at the boundary (via the source-type path above) and converts to the Go func the provider
method expects at dispatch — the full story is [3.5.14](3.5.14-function-provider.md) and
[2.1](2.1-typed-slots.md) §Calling into Starlark.

## 5. What Developers Write vs. What Codegen Produces

**The shape is the contract** for adding a provider resource -- sealed across every provider under
[#625](https://github.com/NobleFactor/devlore-cli/issues/625), enforced at announcement under #646. A provider
resource is:

1. an **exported interface** embedding `op.Resource`, sealed by an **unexported method of its own** -- by convention
   `sealedResource()` -- so no type outside the package can satisfy it (`op.Resource`'s own unexported methods do not
   count as the seal);
2. an **unexported struct** embedding `op.ResourceBase`, declared in the same package, whose pointer implements the
   interface and carries the domain methods;
3. two registrations in the provider's **own `init`**, which Go runs before the generated package's because the
   generated package imports the provider: `op.RegisterResourceImplementation(reflect.TypeFor[X](),
   reflect.TypeFor[x]())` -- the struct reflection runs against -- and `op.RegisterResourceMint(reflect.TypeFor[X](),
   reflect.TypeFor[*x]())` -- what a bare authored string claims as;
4. environment-aware constructors (`Discover<X>` / `New<X>`, optionally source-typed per §3) that **return the
   interface**, passing `reflect.TypeFor[X]()` to `op.NewResourceBase` so the type id is the interface's.

`CheckSealedShape` (`pkg/op/resource_implementation.go`) checks items 1 and 2 and their pairing -- the interface
embeds `op.Resource` and declares its own seal; the registered implementation is a struct, unexported, in the
interface's package; its pointer satisfies the interface -- in the order a reader diagnoses in, and the announcement
refuses the first rule broken by name. The accepted cost: `%T` prints `*service.resource` while the type id says
`service.Resource`; matching one against the other is wrong by construction.

**Developer writes** (`resource.go` in the provider package): items 1 through 4.

**Codegen produces** (`gen/<resource>.gen.go`): the `init()` announcing the interface with its constructor wiring and
the announced method parameters, read from the implementation. The developer never writes that `init()` and never
touches the announcement.

## 6. Registration Sequence

```text
Import phase:   the inventory blank-imports every provider gen package
init() phase:   <provider>/resource.go  → op.RegisterResourceImplementation + op.RegisterResourceMint
                                          (the provider's own init runs first: the gen package imports it)
                gen/provider.gen.go     → op.AnnounceProvider(...)     (the provider + its methods)
                gen/<resource>.gen.go   → op.AnnounceResource(...)     (each resource type; CheckSealedShape refuses
                                          any shape but a sealed interface over an unexported struct)
On demand:      conversion / the planner / rehydration resolve constructors through the receiver registry
```

One registry, announced at init, consumed everywhere — the provider and resource halves are symmetric.
