## Core Idea

A **Provider** is a Go struct with methods that implement a capability domain (files, packages, networking, …).
Each provider is *projected* onto two Starlark surfaces — **Immediate** and **Planned** — from a single source of
truth. The projection is **runtime reflection guided by announced metadata**: the reflection bridge (`goReceiver`)
surfaces methods and fields, and the generated announcement supplies what reflection cannot (parameter names,
optionality, defaults, property modifiers).

```
                    ┌──────────────┐
                    │   Provider   │  one Go struct, hand-written
                    └──────┬───────┘
                           │  AnnounceProvider (generated metadata)
              ┌────────────┼────────────┐
              ▼                         ▼
     ┌────────────────┐       ┌─────────────────────┐
     │   Immediate    │       │      Planned        │
     │ file.exists()  │       │ plan.file.link(...)  │
     │ → value now    │       │ → invocation handle │
     └────────────────┘       └─────────────────────┘
```

**Immediate** methods execute during script evaluation and return concrete values — they drive control flow.
**Planned** methods defer execution: the call records a detached `*op.Invocation` in the session ledger
([3.5.3](3.5.3-plan-provider.md)) and returns it, wrapped as a receiver — the **promise** that wires dependencies.

## The Promise Model

The planned projection builds the dependency graph from the values that flow between calls:

```python
src = plan.file.read_text(resource="config.toml")      # → invocation A
plan.file.write_text(destination_path="/etc/app.toml",
                     content=src)                       # → invocation B; edge A→B at assembly
```

Passing invocation A's handle as an argument records a promise — "this input is A's result" — and the dependency
edge materializes at graph seal ([2](2-execution-graph.md)). Three binding kinds make this work
([2.1](2.1-typed-slots.md)):

| Binding | Set when | Resolved |
|-----------|----------|---------------|
| **Immediate** | the argument is a concrete Starlark value | plan time |
| **Promise** | the argument is another planned call's handle | dispatch time — the producer runs first |
| **Variable** | the argument is a frame binding — `plan.variable("item")`, `plan.item("field")` | resolve time, per frame |

### Gather — Parallel Fan-Out

`gather` materializes its `body` once and dispatches it once per `item`, in parallel up to `limit`
([3.5.2](3.5.2-flow-provider.md)):

```python
plan.gather(
    items=["go", "node", "rust"],
    limit=2,
    body=[plan.pkg.install(packages=plan.variable("item"))],
)
```

Each iteration is its own dispatch frame — `plan.variable("item")` resolves per frame; the body is never duplicated
per iteration. To barrier on every iteration, consume the gather's handle in a downstream slot.

## Registration

One mechanism, no callbacks ([3-operation-namespaces.md](3-operation-namespaces.md) is the how-to):

1. Each provider's generated `gen/provider.gen.go` calls
   `op.AnnounceProvider(reflect.TypeFor[Provider](), roles, constructor, methodMetadata)` at init — roles
   (`RoleAction` / `RoleModule`), the environment-taking constructor, and per-method Starlark metadata.
2. The **receiver registry** (`op.ReceiverRegistry()` — one process-global registry, consolidated 2026-06-09)
   parses the metadata into receiver types; providers are constructed against the `*op.RuntimeEnvironment` on
   demand and cached per environment.
3. The generated **inventory** (`pkg/op/inventory`) blank-imports every announced package — linking a provider in
   is automatic.

Resource types announce the same way ([4.3](4.3-resource-registration.md)). There is no `Register` callback, no
`ActionRegistry`, no generated receiver files — the receivers are projected at runtime by the bridge.

## The Projection Machinery

The machinery lives in `pkg/op/starlarkbridge` and the plan provider:

- **`goReceiver`** — the reflection bridge wrapping any Go value as a `starlark.HasAttrs`: fields as read-only
  properties, methods as callables, announced metadata layered on (Member Projection below).
- **The Converter** — the one Starlark↔Go conversion machine, carrying the session environment
  ([2.1](2.1-typed-slots.md) §The Converter).
- **The plan provider's three-tier surface** — sub-namespace **adapters** (`plan.file.…`), promoted root-provider
  methods (`plan.gather`), and the provider's own methods ([3.5.3](3.5.3-plan-provider.md)). The adapter holds no
  business logic; dispatch decisions live in the plan provider and each method's `op.Planner`.

## The User Experience

The prefix tells you *when* something happens:

| Syntax | When | Returns | Use for |
|--------|------|---------|---------|
| `file.exists("path")` | now, during evaluation | `True` / `False` | control flow, decisions |
| `plan.file.link(...)` | later, during execution | an invocation handle | declaring desired state |

The "double-check" bug — code to check *if* something exists and separate code to *make* it exist — disappears:
the immediate projection queries state, the planned projection declares intent, and they compose because they are
projections of the same capability.

## Access Directives

The struct-level `+devlore:access` directive routes the provider onto surfaces:

| Directive | Immediate | Planned |
|-----------|-----------|---------|
| `+devlore:access=immediate` | yes | — |
| `+devlore:access=planned` | — | yes |
| `+devlore:access=both` | yes | yes |

Per-method surface refinement rides the announced metadata's `Modifiers` channel (e.g. `+devlore:property`, Member
Projection below); `+devlore:root=true` promotes a provider's methods flat onto `plan.*`
([3.5.2](3.5.2-flow-provider.md)).

## Pluggable brokers — provider-owned routers

Some providers extend through **brokers**: interchangeable backends, each yielding a specific kind of resource, that the
provider mediates so a caller never knows which backend served a request. This is the Broker pattern (POSA). A **broker
is any type that fulfills the provider's broker interface** — no base to embed, no registration, no required home for
the type; satisfying the interface is the whole contract.

This is "broker" in the sense of the **Open Service Broker API** and a credential broker like Vault — a request/response
mediator of interchangeable backends — *not* the message-broker (Kafka, RabbitMQ) sense. Brokers here carry no queuing,
ordering, or delivery-guarantee semantics; nothing about the pattern is inherently queue-like, the queue association
belonging only to the message-broker family.

**The provider owns a router; the router owns its sub-brokers.** Each brokered provider has a **router** — itself a
broker (it implements the interface `B`) that, rather than doing the work, **allocates and configures its sub-brokers
from the config passed to its constructor and delegates** to one or more of them. The router is obliged to honor that
config; *which* sub-brokers it brings up, in what order, and with what failover or fan-out, is the router's own rule.
The existing `compositeManager` (`pkg/platform/composite.go`) — which fans out to apt/dnf/brew leaves and routes by
package type — is exactly this router, and becomes the `pkg` provider's router.

**The pattern is recursive, and it unifies brokers and services.** A broker is either a **leaf** (does the work,
configures itself from its config node) or a **router** (allocates sub-brokers from its config node and delegates), and
a sub-broker may itself be a router. So a "service" is just a leaf sub-broker, and a broker fronting several backends
*is* a router over them — one recursive role, every node satisfying `B`:

```text
elevation router   (elevation.Broker)        ← provider builds it from base.providers.elevation.brokers
 ├─ ssh router    (elevation.Broker)         ← allocates from …brokers.ssh (failover: [step-ca, vault-ssh])
 │   ├─ step-ca   (elevation.Broker, leaf)   ← configures itself from …ssh.step-ca; mints
 │   └─ vault-ssh (elevation.Broker, leaf)
 └─ sudo          (elevation.Broker, leaf)
```

**The config tree is the broker tree.** Construction walks the resolved config: the provider builds its top router,
handing it `providers.<name>.brokers`; that router allocates each sub-broker, handing each *its* config node; the
recursion bottoms out at the leaves. The typed config node a broker receives is exactly what it is obliged to allocate
and configure from — so the path-keyed child-type schema (typing `brokers.ssh`, `brokers.ssh.step-ca`, …) and the
runtime broker tree are the same structure read twice.

So the broker model is a **pattern, not framework machinery**. `op` supplies only the broker **interface** `B` (defined
per provider/domain — the package-management interface, `elevation.Broker`) and the **typed config tree** that hands
each broker its node. There is no `op.AnnounceBroker`, no `op.WireBrokers`, no global registry, and no
`op.BrokerRegistry` trait: the provider-written router allocates, holds, and routes its own sub-brokers
(`compositeManager` does exactly this today, by hand). `op.BrokerBase` survives only as an optional convenience, never a
requirement.

**Two interfaces, and the lifecycle lives on the far one.** A broker sits between two contracts. The
**provider → broker** contract — the framework's — is deliberately minimal: acquire a credential of the broker's kind,
and revoke it. That is the invoker's entire view; it never sees catalogs, service instances, bindings, or plans. The
**broker → backing service** contract is whatever the backend demands — an SDK call, a CLI, or the full Open Service
Broker lifecycle (catalog → provision → bind, with a plan selected). The broker absorbs all of it. So OSB's verbs, when
they apply at all, live on the broker → backend interface, never on provider → broker — which is why the framework
contract stays `mint` / `revoke` and does not take on the OSB verb set. A backend choice such as a Plan/SKU is therefore
**configuration**, set in the broker's config sub-tree (and so subject to the profile overlay); the provider never knows
a plan exists. Per-request plan variation travels as an attribute of the offer flowing through — the provider passes it
along without interpreting it. Selecting a *specific* broker for an individual request is the router's **dispatch**
(POSA's Lookup), distinct from allocation.

## Member Projection — Fields, Methods, and Properties

A Go type's members reach its starlark surface by three rules, applied by the reflection bridge (`goReceiver`)
and, where it adds value, by codegen:

- **Exported fields → read-only properties.** Exported struct fields project as eager attribute reads
  (`x.field`) via reflection — no codegen. They are read-only: `goReceiver` implements `starlark.HasAttrs` but
  not `HasSetField`, so `x.field = v` is rejected. Mutation happens only through methods.
- **Methods → methods.** Exported methods project as callables (`x.method(...)`). Without codegen, **parameter
  names are unavailable** — Go reflection does not expose them — so arguments are positional only.
- **`+devlore:property` → method-as-property.** Codegen marks a **parameterless, value-returning** method
  (`() T` or `() (T, error)`) so attribute access eager-invokes it and yields the result instead of returning the
  callable (see [3.3](3.3-static-starlark-codegen.md), archived). Actions (no value) are ineligible.

**When to codegen — the upside criterion.** Runtime reflection already surfaces any returned type ad hoc
(`op.ReceiverRegistry().TypeByReflectionOrDerive`). Codegen (`AnnounceProvider`/`AnnounceType` with `MethodMetadata`)
is applied to a type only when a method has an upside reflection cannot deliver:

- **Named parameters** — a kwargs-called method needs codegen-emitted parameter names (reflection gives only
  positional names).
- **Property semantics** — `+devlore:property` requires the codegen-emitted `Modifiers` channel.

A type whose methods need neither is left to reflection (positional methods, field-properties) — no codegen.

**Type discovery: pointer-return walk plus a property-tag struct scan.** Codegen finds dependent types two ways.
From provider-method returns it follows pointer returns (`*Type`) transitively. And it enumerates package structs
for any carrying a `+devlore:property` method that the return-walk can't reach — e.g. a `Decl` implementer surfaced
only through an interface-typed field (`SourceFile.Decls` is `[]Decl`), which no method return points at. At
runtime, projection then handles every value shape via reflection — scalars, slices, maps, structs, and interface
values (which unwrap to their concrete).

**Interface-typed members project through the concrete value; eager-property tags live on the concrete
implementers.** When a field or return is an interface (`Decls []Decl`, or a method returning `Decl`), the bridge
unwraps the value to the concrete behind it and resolves that concrete type's registered receiver type via
`op.ReceiverRegistry().TypeByReflectionOrDerive`. The concrete is the single source of both **dispatch** (its
methods carry receiver-bound funcs) and **metadata** (its registered `MethodMetadata`). The interface itself is
never registered or dispatched: it cannot dispatch (an interface method carries no receiver-bound func), and its
eager-property tag would need codegen that cannot target an interface — so eager properties on interface-member
methods are tagged on the concrete implementer structs, discovered by the property-tag struct scan.

**`any` (empty interface).** Inbound (starlark → Go) the framework refuses to interpret `any`: a `Projector`-bearing
wrapper (`*goReceiver`, `*Promise`) projects via `Project(reflect.TypeFor[any]())`, and `Convert`'s empty-interface
step returns the wrapped value verbatim, preserving pointer shape. Outbound (Go → starlark) an `any` unwraps to its
concrete like any other interface value and projects that surface.

**Type resolution is environment-free.** Projecting a Go value resolves its *receiver type* — registered
`MethodMetadata` — which is **global declaration data** owned by the package-level registry, not by any execution.
The `RuntimeEnvironment` is owned by exactly two things, neither a value type: the two **provider kinds** (service
and resource providers, each minted by an environment-taking constructor) and the **`ActivationRecord`**.
**Consolidated to one registry (2026-06-09):** the per-execution `RuntimeEnvironment.ReceiverRegistry` field and the
`ResolveReceiverType` free function were removed; there is exactly one registry — reached everywhere through
`op.ReceiverRegistry()` — so "resolve type info through the env" is no longer a mistake the API permits. Registered
lookups are fast reads; unregistered types derive under a mutex, safe for concurrent dispatch.

**Value vs. pointer returns.** A type is returned by **pointer** when it has identity and in-place mutation
(interned in an index, or mutated through shared references); by **value** when it is a small immutable data
record. **Compute-heavy methods are not properties** — a property eager-evaluates on every access, so per-call
recomputation stays a method; immutable derived data precomputes into exported fields (cheap field-properties).

## Consumers

| Tool | Relationship |
|------|-------------|
| **star** | authors the projection: the codegen (pinned to its Last-Known-Good snapshot) reads providers and emits the announcements, action-name constants, and resource gen files (`make generate`). Star's own tool providers live under `cmd/star/provider/` with their own inventory. |
| **lore** | plans through the shared plan provider's **Go door** (`Provider.Plan`) and the Starlark door alike — its builder and `.star` phase scripts pool invocations in one session ledger ([3.5.3](3.5.3-plan-provider.md)). |
| **writ** | the deploy family (deploy / upgrade / decommission / adopt / migrate) plans through the same door and executes through `op.GraphExecutor` + the trace store (phase-8 steps 33/47) — no imperative node construction remains. |
| **devlore-test** | drives the announced surface end to end: 60+ fixtures assemble and run graphs through `plan.*`. |

All consumers share one substrate: the receiver registry, the plan provider, the sealed graph, the executor.

## Design Properties

1. **No duplication.** One Go method is the single source for the immediate call, the planned node, and the
   engine-facing action.
2. **Safety by construction.** Access zones route methods to surfaces; a planned-only method has no immediate
   projection to misuse; signatures are validated at announce.
3. **Automatic dependency wiring.** Passing a handle creates the edge; dependencies emerge from data flow.
4. **One conversion machine, one registry.** The bridge converts; the process-global receiver registry resolves —
   no parallel systems to drift.
