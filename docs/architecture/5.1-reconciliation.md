# Audit, Reconciliation, and Recovery in the Execution Graph

> **Status:** rewritten 2026-07-22 (phase-8 step 51, slice 4). The previous body was a **draft plan** (issue #156,
> 2026-02/03) proposing an `ExecutionEvent` envelope, a 4-value `Do` return, per-action `Reconcile<X>` methods, and
> an `EventSink` / `AuditLedger` / `ReconciliationStore` pipeline — **none of which landed** (verified 2026-07-22:
> zero tree hits for all of them; `writ reconcile` itself was replaced by `writ status`). The three concerns were
> realized by other means, recorded below; the proposal is preserved as an explicitly unimplemented appendix.
> Companion: [`5.1-reconciliation.status.md`](5.1-reconciliation.status.md).

## Governing Principle

**The action is the subject-matter expert on *what* changed and *how* to fix it. The executor is the objective
observer of *when* and *how* the process unfolded.** The action knows the resource, its identity, and its state;
the executor knows the timeline, the correlation, and the outcome. Neither trespasses on the other's domain.

The landed realization: the action's knowledge rides its **receipt** (what the dispatch actually did, sufficient to
undo it — [2.2](2.2-phase-execution.md)) and the catalog's recorded **content identity** (Etag + Digest per active
resource — phase-8 step 48); the executor's knowledge rides the **trace** envelope (per-dispatch outcomes, the
transition journal, the terminal `RunStatus`). The framework never computes a provider's checksum — the provider
records its own facts, and the framework carries them.

### Provider Access Contexts

The provider is the same code in every context — it is the boundary that changes. A provider returns clean errors
and clean results; the boundary layer adds meaning:

| Context | Boundary layer | What the boundary knows | Context it adds |
|---------|---------------|------------------------|-----------------|
| **Application** | Go call site | CLI command, user intent | feature-appropriate wrapping (`"backup failed: %w"`) |
| **Planning** | Starlark receiver / planner | plan location, slot bindings | plan-time location and validation context |
| **Executing** | the executor | unit ID, action name, attempt, timing | the receipt + trace envelope |

Method claims ([3.6](3.6-method-classification.md)) model which methods are available in which contexts;
error wrapping follows the same boundary — the provider is context-agnostic, the caller is context-aware.

## Drift Detection — the Landed Model

`writ reconcile` no longer exists; **`writ status` replaced it** (phase-8 step 47), and the mechanism is **recorded
content identity**, not per-action probe methods:

1. **At deploy**, the trace's ledger snapshot records each active resource's `Etag` (the cheap screen) and `Digest`
   (canonical content identity) — the as-deployed record (step 48).
2. **At status**, the readback classifies each target against that record: fresh, **stale** (source changed since
   deploy), **modified** (target changed out-of-band), or conflicting — attribution falls out of comparing the live
   state against the recorded source and target identities. A missing run index is a hard error, not a silent
   rescan; there is no `--fix` (re-deploying is the explicit, separate act).
3. **At upgrade**, the same attribution decides posture: source-changed re-renders; target-modified is surfaced
   rather than silently overwritten (the conflict policy's pre-flight — step 49).

The principle survives from the original design: the *provider's recorded assertion* is what drift is measured
against — a git repository's dirty-aware `Digest`/`Etag` ([3.5.10](3.5.10-git-provider.md)), a file's canonical
content digest — and the framework compares records, never interpreting resource internals.

## Recovery Safety — the Landed Gates

The proposal's "reconcile before undo" safety gate landed in three distributed forms rather than a stack-level
`Reconcile` pass:

1. **Compensation is mechanical; receipts are precise.** A compensating action restores exactly what its receipt
   records (`MutationKind`-dispatched for files — [3.5.4](3.5.4-file-provider.md)); it does not guess.
2. **The recovery-digest tamper check.** A file receipt records the digest of its archived bytes; compensation
   re-hashes the recovery archive and refuses a tampered restore.
3. **The resumed unwind is state-checked** ([2.2](2.2-phase-execution.md) §Serialization and resume;
   [compensation-failure-contract.md](../plans/extract-starlark-from-op/phase-8/compensation-failure-contract.md)).
   When a compensation itself fails, the run lands `stopped × compensation_failed` — fail loudly, persist the
   journal, emit restart instructions. On restart, `ResumeUnwind` re-runs the unwind **observing reality rather
   than assuming the recorded plan**: each compensator re-queries actual state and undoes only what is still
   present (an operator's hand-cleanup no-ops through the compensators' own tolerance). A clean pass de-escalates
   to `stopped × execution_failed` — the clean baseline from which re-running forward is a fresh, explicit run.

## Relationship to the Writ Lifecycle

| Lifecycle | What happens | Record consumers |
|-----------|-------------|------------------|
| **Deploy** | build → persist the plan → execute → persist the trace | receipts (rollback), trace (audit), ledger snapshot (drift anchor) |
| **Status** | fold the run index; classify against recorded identity | the drift report — no mutations, no recovery stack |
| **Upgrade** | constrained re-deploy with drift attribution | all three; new snapshots supersede in the index |
| **Decommission** | reverse traversal, receipts for the removals | recovery + trace; index records the removal run |

## Relationship to Hooks and Events

The original plan's `EventSink` ("expose the event stream from the executor so consumers can subscribe") was an
early sighting of what became the **observability surface**: the lifecycle-hook seam feeding an app-agnostic event
stream, orthogonal to narration and control — designed in [2.8](2.8-eventing-infrastructure.md) and chartered as
phase-8 step 50. Audit does not ride that stream; audit is the trace. The stream is live observation; the trace is
the durable record.

## Appendix A — Proposed: the `ExecutionEvent` / `Reconcile` triangle *(design only — not implemented)*

> Verified 2026-07-22: no `ExecutionEvent`, `EventSink`, `AuditLedger`, `ReconciliationStore`, `ErrDrifted`, or
> `Reconcile<X>` provider methods exist in the tree; `Action.Do` remains three-valued. Preserved for a future
> charter; several of its ideas landed transformed (noted inline above).

**The proposal.** Extend `Do` to a 4-value return — `(Result, Compensator, ReconciliationState, error)` — where the
reconciliation state is the action's *expected-state anchor* (content hash, version, status token) captured at the
moment of completion. Add a per-provider `Reconcile<X>(state) (drifted bool, err error)` probe, enforced by codegen
as a **type-signature triangle** (`X` / `Compensate<X>` / `Reconcile<X>`, with the third return of `X` matching the
first parameter of `Reconcile<X>`). Wrap every dispatch in an `ExecutionEvent` envelope routed to three consumers:
the recovery stack (mechanical reversal), an append-only audit ledger, and a reconciliation store keyed by external
resource id. Make `Unwind` run reconcile-before-compensate, skipping drifted entries with `ErrDrifted` — automated
undo of a manually modified resource is dangerous.

**Where its ideas went:** the envelope and audit ledger → the trace's receipts + journal; the expected-state anchor
→ the ledger snapshot's Etag/Digest (recorded once, compared at status/upgrade — cheaper than N probe methods); the
reconcile-before-undo gate → the receipts' precision, the recovery-digest tamper check, and the state-checked
resumed unwind; the event stream → the 2.8 observability design. **Not carried:** the per-action `Reconcile`
probe surface and the resource-keyed cross-graph store (the "sidecar" aggregating records to detect cross-graph
drift on shared resources) — the latter remains an open idea for the distributed model
([1-system-model.md](1-system-model.md) §6.2).
