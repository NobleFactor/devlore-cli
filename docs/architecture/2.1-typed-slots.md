# Typed Slots and the Binding Model

> **Status:** rewritten 2026-07-22 (phase-8 step 51, slice 1) onto the landed `pkg/op` model. The pre-`op` body —
> `SlotValue`, the `Context.Data` property bag, `RegisterReflectedActions` / `ActionRegistry`, engine slot-filling —
> is replaced. Three phase-8-era sections are preserved: **Plan-Time Conversion**, **The Converter**, and **Calling
> into Starlark** (the Invoker text re-verified against the tree 2026-07-22). Companion:
> [`2.1-typed-slots.status.md`](2.1-typed-slots.status.md).

## Thesis

Slots are how units receive inputs. A slot is filled by a **binding** from the sealed `op.Binding` set; a binding's
**type** is dictated by the provider method's Go signature (the signature *is* the specification); and values cross
the Starlark↔Go boundary through exactly one conversion machine (`op.Convert` + `starlarkbridge`). What the
pre-`op` design solved with a global property bag (`Context.Data`) is now the **variable surface**: declared
parameters resolved against the application's sources, layered frames, and explicit variable bindings.

## Terminology

| Term | Origin | Meaning |
|---|---|---|
| **Receiver** | Starlark | An object with methods — `file`, `plan.file`, `git`. |
| **Namespace** | Ours | The grouping tying a provider to its receivers, methods, and actions; the provider's package name (`file`, `pkg`). Appears in action names (`file.link`), method paths (`plan.file.link()`), and error messages. One provider per namespace. |
| **Provider** | Ours | The hand-written Go struct whose methods are the business logic; announced with metadata at init ([3-operation-namespaces.md](3-operation-namespaces.md)). |
| **Access zone** | Ours | `planned` (methods plan nodes for later execution), `immediate` (methods execute at script evaluation), or `both` ([3.5-provider-catalog.md](3.5-provider-catalog.md)). |
| **Slot** | Ours | A named, typed input on a unit, filled by a binding. |
| **Binding** | Ours | One of the sealed `op.Binding` implementations below. |
| **Promise** | Ours | A binding to another unit's result, resolved at dispatch. |
| **Variable** | Ours | A binding to a named runtime value, resolved against the run's variable surface. |
| **Receipt** | Saga | A compensable action's undo evidence ([2.2-phase-execution.md](2.2-phase-execution.md)); the pre-`op` `map[string]any` compensation state is gone. |

## The sealed Binding set

`pkg/op/binding.go` ([2-execution-graph.md](2-execution-graph.md) owns seal mechanics):

| Binding | Meaning | Resolved | Serializes as |
|---|---|---|---|
| `ImmediateBinding` | a Go value known at plan time | plan time | the value |
| `PromiseBinding` | another unit's result, by unit ID | dispatch time | the reference |
| `VariableBinding` | a named variable, optional field projection | resolve time | the name (+ field) |

Promise bindings are structural: dependency edges derive from them at graph seal, and the plan-time validation pass
type-checks every producer → consumer pair (`checkPromiseTypes`, `pkg/op/validate.go`) so a promised value that
cannot convert to the consuming parameter fails at plan time, not dispatch.

## Variables — the runtime value surface

The pre-`op` `Context.Data` bag (a `map[string]any` the engine poured into unfilled slots) is gone. In its place:

1. **Declared parameters.** `Graph.Parameters()` is the bubble-up variable surface — the named, typed inputs the
   graph's units actually reference.
2. **Source resolution at run head.** `GraphExecutor.Run`'s preflight resolves that surface against the
   application's source maps (flags, config, environment — the roll-up is [configuration.md](configuration.md)'s
   concern), with **caller-supplied variables layered on top** as the highest-priority source.
3. **Frames.** Each subgraph scope inherits its parent's variable frame; `gather` mints a per-iteration frame
   binding `item`; `plan.variable("name")` reads the surface, and `plan.item("field")` projects one field of a
   record value at resolve time (phase-8 step 45).

Capabilities that used to ride the bag as function values (`decryptor`, `git_mv`, …) no longer do: they live where
they belong — the SOPS client on the encryption provider, the recovery site on the runtime environment, a Starlark
callback as a content-addressed `function.Resource` (below). A graph document therefore serializes **bindings, not
runtime state**: immediates by value, promises and variables by reference — the plan is complete, and the runtime
configuration arrives at run time by resolution.

## Slot typing — the signature is the specification

A slot's name is the snake_case form of the provider method's parameter name; its type is the parameter's Go type.
The announced `MethodMetadata` carries the surface Starlark sees — parameter names, optionality, and defaults
(including computed forms like `chmod?={{ umask 0o666 }}`) — generated from the signatures
(`gen/provider.gen.go` per provider).

Baseline Starlark mappings (the general rule is the conversion cascade below):

| Go type | Starlark type |
|---|---|
| `string` / `bool` / `int` | `String` / `Bool` / `Int` |
| `[]string`, `[]any` | `*List` |
| `map[string]any` | `*Dict` |
| `os.FileMode` | `Int` (e.g. `0o644`) |
| `*starlark.Function` | a content-addressed `function.Resource` ([3.5.14](3.5.14-function-provider.md)) |

## Plan-Time Conversion

Starlark type mappings cover scalars and collections. The general rule is broader: at plan time, **each immediate
argument is converted against its parameter's Go type** by the global `op.Convert` cascade (`pkg/op/convert.go`),
driven by whether the value is already a `Resource` and, if so, its **addressing**
([4.1-resource-identity.md](4.1-resource-identity.md)). `op.ActionPlanner.Plan` (`pkg/op/planner.go`) applies it to
every action argument:

- **A plain value** (string, int, …) converts toward the parameter type **now**. A reference-resource target is built
  at plan time — `file.copy(from="a.txt")` resolves the string to a file resource via
  `TargetConverter.CanConvertFrom` and catalogs it. Plain-to-plain is identity / assignability.
- **A content-addressable `Resource`** (`AddressingContent` — e.g. a `function.Resource` produced at the starlark→Go
  boundary) is **validated now and converted at runtime**. The planner asserts `SourceConverter.CanConvertTo(param)`
  exists, then stores the resource; the conversion runs at `Method.Invoke`. Its product is often an ephemeral native
  value — a Go func pointer for `file.walk_tree(fn=…)` — that cannot serialize into a saved graph, so the *resource*
  travels and the conversion is deferred.
- **A location `Resource`** (`AddressingLocation`) converts **now** — location-based conversions (a file resource to
  its path string) are serializable.

**The addressing contract.** An `AddressingLocation` resource converts along its *location* (file resource ⇄ path);
an `AddressingContent` resource converts along its *content* (`function.Resource` ⇄ bytecode / func). The planner
enforces this with a two-case switch on `Resource.Addressing()` — any other addressing is unreachable by assertion.

**The platform comes for free.** Plan-time resource construction needs a `Platform` (e.g. `pkg.Resource` resolves its
purl type from the platform — the manager→purl-type matrix lives in `pkg/platform`). `NewRuntimeEnvironment`
defaults `Platform` to `platform.Detect()` when none is set. Execution always runs on the detected host;
`WithPlatform` is only an explicit override for cross-platform planning (build a Linux graph from a Darwin host).

## The Converter

starlark → Go conversion is encapsulated in `starlarkbridge.Converter`, a small value that carries the session's
`RuntimeEnvironment`. It holds the environment because conversion sometimes *constructs resources*: a
`*starlark.Function` argument becomes a content-addressable `function.Resource` via `function.NewResource(env, …)`,
and resource construction consults the receiver registry. Keeping the environment on the converter makes it
available wherever a value is converted — at any nesting depth, since a function nested in a list or dict is reached
by the same recursive `toNaturalGo`.

Ownership is **`Runtime` 1 → 1 `Converter` 1 → n `goReceiver`**: a `Runtime` owns one `Converter` (built from its
environment) and hands that same converter to every `goReceiver` it builds. Every receiver must convert the starlark
arguments of a method call into the Go types its provider method expects, and some of those are resources that need
the environment — so every receiver needs the converter. The plan provider converts identically, from the same
session environment.

## Calling into Starlark

The reverse direction arises when a Go-side action must *invoke* a Starlark function the script supplied — a planned
`file.walk_tree(fn=…)` hands `file.Provider.WalkTree` a Starlark reducer it calls per entry. The function is
captured at plan time as a content-addressable `function.Resource`; at execution `op.Convert` turns it into the
`file.Reducer` the method expects via `reflect.MakeFunc` — a manufactured Go func whose body converts its arguments
*to* Starlark, calls the function, and converts the result *back*. That conversion is the mirror of *The Converter*
and uses the same single implementation — notably wrapping a file resource argument as a `goReceiver` so the reducer
can receive it.

`op` and the resource packages stay Starlark-agnostic: the calling machinery lives in `starlarkbridge` as
**`starlarkbridge.Invoker`**, consumed by `function`. Each `function.Resource` holds its **own** invoker, built at
construction (`starlarkbridge.NewInvoker()` is environment-free on the conversion path) — per-resource instances,
never a process singleton. There is exactly one Go↔Starlark converter — the bridge — and providers never roll their
own. Each call runs on a **fresh Starlark thread**: threads are not safe for concurrent reuse, so the bridge mints
one per call rather than sharing a session-wide thread.

## Action dispatch

The pre-`op` `RegisterReflectedActions` / `ActionRegistry` machinery is gone. Today:

1. **Announce with metadata.** Each provider's generated descriptor calls
   `op.AnnounceProvider(reflect.TypeFor[Provider](), role, constructor, methodMetadata)` at init; the receiver
   registry classifies each method by its return shape — pure, fallible (`…, error`), or compensable
   (result + `Compensator` + error, with a `Compensate<Name>` pair validated at registration).
2. **Activation-first.** Every provider method takes the `*op.ActivationRecord` first (the step-27 floor); the
   engine-facing form is `Action.Do(activationRecord) (Result, Compensator, error)` (`pkg/op/action.go`).
3. **Reflect once.** The name→method resolution and argument shapes are baked into typed invoke adapters at
   registration (phase-8 step 43) — reflection is paid once per registered action, and the dispatch loop makes plain
   calls.
4. **No `Undo`.** Compensation routes through receipts naming their compensating action
   ([2.2-phase-execution.md](2.2-phase-execution.md)) — there is no per-action `Undo` method.

## Error reporting

Errors use Starlark names, not Go names: the slot name (`template_data`), the Starlark type vocabulary (`dict`), and
the namespaced method (`plan.file.render`) — `plan.file.render: slot "template_data" requires dict, got string`.
The conversion machinery owns the vocabulary in both directions, so the mapping table drives conversion and error
text alike.
