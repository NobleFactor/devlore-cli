# Method Classification — Pure, Query, Action

> **Status:** design (draft, 2026-08-19). Establishes a per-method classification from which namespace placement
> and hermeticity both derive, replacing the retired provider-level access directive. No implementation. Companion:
> [`3.6-method-classification.status.md`](3.6-method-classification.status.md).
>
> **Relationship to the neighbours.** [`3.2-projected-provider-api.md`](3.2-projected-provider-api.md) describes
> what a provider's methods look like once projected into Starlark, and
> [`3.3-static-starlark-codegen.md`](3.3-static-starlark-codegen.md) how the projection is generated. **This
> document owns the property that decides where a method may appear and when it may run.**
> [`2.4-hermeticity-guarantees.md`](2.4-hermeticity-guarantees.md) states the guarantee this exists to make
> enforceable.

## Thesis

**Classify methods, not providers.** The retired access directive was attached to a provider, but the property it
was trying to describe belongs to individual methods — and its `both` value is the evidence: it did not describe
a provider at all, it said *"this provider's methods are not all the same kind."*

`file` is three things wearing one name:

```
file.join, file.name, file.parent          value in, value out
file.exists, file.read_text, file.glob     reads the host
file.write_text, file.copy, file.remove    changes the host
```

One annotation covering all three cannot be right about any of them, and today it is wrong in the dangerous
direction: because `file` is `access=both`, `file.write_text` is callable during planning, outside the graph,
with no receipt, no compensation and no trace ([#563](https://github.com/NobleFactor/devlore-cli/issues/563)).

## 1. Three kinds

| Kind | Effects | Namespace | Admitted to a hermetic runtime |
| --- | --- | --- | --- |
| **pure** | none beyond its arguments | immediate | yes |
| **query** | reads host state | immediate | no |
| **action** | changes host state | `plan.*` only — must be a graph node | no |

Two things fall out of one property.

**Namespace placement derives.** An action changes the world, so it must be a graph node, so it must be
reachable only through `plan.*` — that is what earns it a receipt and a compensation. Pure and query methods
return values to a script and belong in immediate scope. `immediate` / `planned` / `both` were describing this
consequence rather than its cause.

**Hermeticity derives.** A hermetic evaluation admits `pure` and nothing else.

And the hole closes by construction rather than by filtering: unrecorded mutation during planning stops being
expressible, because a mutation is an action and an action is a graph node.

## 2. Attribution is optional, not required

Only one misclassification opens a hole: **claiming `pure` for something impure**. Everything else is safe.

- An action misclassified as query or pure is **caught for free** (§3.1).
- A pure method left unclassified is treated as a query — over-restrictive, surfacing as *"why can't I use
  `file.join` here"*. Annoying, safe, self-correcting.

Requiring an attribution on every method does not reduce the dangerous error; it adds ceremony to the safe ones.
Worse, it **manufactures** the dangerous error where none needed to exist. `platform.Hostname() string` takes
nothing and cannot fail, so `pure` is a plausible wrong answer — but left unannotated it defaults to query,
which is correct, with no decision made and no opportunity to get it wrong.

**So: annotate `pure`. Everything else is inferred or defaulted.** The default is `query`, which fails closed.

## 3. What codegen checks

### 3.1 Receipt implies action — total, cheap, already conventional

Provider methods that change the world return a receipt, and the repository already organizes provider files by
return signature under Fallible / Actions / Compensable delineators. So the action tier needs no annotation at
all:

```go
Copy(…)   (*Regular, *Receipt, error)     → action
Exists(…) (bool, error)                   → not an action
Join(…)   string                          → not an action
```

Any attribution other than `action` on a method returning `*Receipt` is a contradiction, and codegen rejects it.

### 3.2 A `pure` claim is verified — expensive, and unavoidable

Signature alone cannot separate pure from query, and the failure is in the dangerous direction:

```go
Join(parts ...string) string      pure
Hostname() string                 the most machine-dependent call in the codebase
```

Both take arguments and return a string that cannot fail. The signature encodes **failure and undo**, never
**provenance** — where the answer came from is invisible at the boundary.

So a `pure` claim must be checked against the call graph: does the method transitively reach `os`, `exec`,
`net`, `time`, or another method not itself pure? Indirection through interfaces and reflection degrades this,
so it is a check that raises confidence rather than a proof.

**This check is required under any scheme**, mandatory attribution included, so it is not a reason to prefer
one over the other.

### 3.3 Codegen emits the derived classification

Optional attribution has one real cost: **silence is ambiguous**. An unannotated method might be a considered
query or a method nobody has thought about, and nothing distinguishes them.

Fixed without paying for mandatory attribution: codegen **writes the classification into the generated file** —
`pure` where declared and verified, `action` where the receipt says so, `query` otherwise. The hand-written
annotation stays the exception; the generated artifact becomes the record. A classification that changes then
appears in a pull request as a changed generated line, which is where a reviewer will actually see it.

## 4. The runtime policy is the second dimension

Classification is a fact about a method. **Which kinds an evaluation admits is a policy of the runtime**, and
neither dimension can express the other:

| Runtime | Admits | Because |
| --- | --- | --- |
| Graph planning | `pure` | [`2.4`](2.4-hermeticity-guarantees.md): same inputs, same graph, any machine, every time |
| `star` | `pure`, `query`, `action` | a scripting utility, where effects are the point |
| `devlore-test` | to be decided | it runs fixtures of both kinds |

`file` is correct as immediate in `star` and wrong in planning — one provider, two verdicts, decided by which
runtime is asking. That is why classification alone is insufficient and
[#563](https://github.com/NobleFactor/devlore-cli/issues/563)'s per-runtime module selection is the other half.

## 4a. Expressibility — a second derived property, on a different axis

Classification answers *what does this method do to the world*. It does not answer *can an author call it at
all*, and those are independent.

**Every resource in the tree currently publishes methods no script can invoke.** They resolve as attributes
and fail one layer deeper, at parameter binding:

```
r.can_convert_from(source="string")
→ param source: string value is neither assignable nor convertible to reflect.Type
```

`file`'s four variants announce `can_convert_from` / `convert_from`; `mem` and `function` announce
`can_convert_to` / `convert_to` / `init`. Their parameters are `reflect.Type` and `*starlark.Thread` — Go
concepts with no Starlark representation, so `op.Convert`'s cascade exhausts every step and reports a
framework internal to an author who never mentioned one.

**This is worse than a missing operation.** A missing one fails immediately and legibly. These resolve, would
appear in any generated reference as available
([#675](https://github.com/NobleFactor/devlore-cli/issues/675)), and fail late.

### Why classification does not catch it

A framework callback has no effects, so it classifies as `query` and stays announced. `CanConvertFrom` exists
for `op.Convert` to call across a package boundary — it is Go-visible because the framework needs it, not
because an author does. **Go's `exported` is doing double duty**: *reachable by the framework* and *callable
by an author* are different sets, and the language cannot distinguish them.

Today only `SKIP_METHODS` does — a hand-maintained list of ten names that catches `Pack` and `Unpack` but not
`ConvertTo`, `CanConvertFrom`, or `Init`. Every hand-maintained surface in this repository has been found
wrong; this one is no exception.

### The rule

**A method whose parameters cannot cross the bridge is not part of the authoring surface.**

Derived, not annotated — the same principle §2 establishes for classification, and for the same reason. The
bridge already owns the answer: `op.Convert`'s cascade *is* the definition of what can cross, and §6 shows
both dispatch modes bottom out in it. Asking it is correct by construction and cannot be forgotten, because a
new callback taking a `reflect.Type` is excluded the moment it is written.

It also disposes of the boundary case cleanly. `Equal(other any)` stays: `any` accepts anything Starlark
produces, and `a.equal(b)` is a reasonable thing to write.

**Emitted like the classification** (§3.3), so a method leaving or entering the authoring surface shows up in
a diff rather than silently.

### Relation to §5

Unlike `template` and `plan`, this is not a case the scheme cannot express — it is a property the scheme was
not asking about. Adding it needs no new annotation and no new judgment call, only a question put to a
component that already exists.

## 5. What this does not fix

**`template` cannot be classified.** Its function map exposes `"Env": os.Getenv`, so purity depends on the
*template text* rather than on the method:

```
template.render_text(content="hello")               pure
template.render_text(content="{{ Env \"USER\" }}")  machine-dependent
```

No per-method attribution can express that. The fixes are removing `Env`, or making the function map
configurable per runtime so a hermetic runtime renders without it.

**`plan` is mandatory for planning and not pure** — `LoadDefinition` reads a graph from disk. Either the
planning runtime admits `plan` on separate grounds, or that method moves out of the provider.

## 6. The two dispatch stacks converge in `op.Convert`

Distilled from the retired stack-comparison sketches (2026-08-20; their line-level stacks described a
superseded shape — `NodeBuilder`/`task_builder.go` no longer exist — but the law they proved still holds and
is worth keeping):

**Both dispatch modes bottom out in `op.Convert`'s single seven-step cascade** (assignable/convertible →
slice recursion → map recursion → `SourceConverter` → `TargetConverter` → registered resource construction →
error). Immediate mode (`goReceiver.dispatch`) unpacks Starlark values to natural Go and converts per
parameter inside `Method.Invoke`, at dispatch time. Plan mode (`ActionPlanner.Plan`) converts at
slot-binding time. There is no duplicate type-matching anywhere — one cascade, two entry points.

**The asymmetry that remains is deliberate**: plan mode converts at slot-fill so the catalog can intern
resources before the node is sealed; immediate mode converts at dispatch because immediate receivers pass
raw values and cataloged resources are a planning concern
([4-resource-management.md](4-resource-management.md) §9 item 3). Same cascade, different timing — the
timing difference *is* the plan/immediate distinction, seen from the converter.

## 7. Open questions

1. **Does `query` belong in immediate scope at all?** It is what makes planning non-hermetic today. Excluding it
   entirely is simpler than a policy dimension, at the cost of `file.exists` during planning.
2. **`devlore-test`'s policy** — its fixtures exercise both immediate and planned modes deliberately.
3. **Migration.** Resolved 2026-08-25 — the provider-level access directive was removed in one pass, with no
   shim. Namespace placement falls to the documented default until this classification is implemented.
4. **Whether the call-graph check gates the build or warns.** Gating on an analysis that interfaces can defeat
   risks blocking on a false positive; warning risks being ignored.
5. **Does expressibility (§4a) gate or warn?** A method dropping off the authoring surface is a breaking
   change to any script that called it; a method that was never callable dropping off is a correction. The
   emitted classification makes the difference visible in a diff, but does not decide which is which.
