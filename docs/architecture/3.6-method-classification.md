# Method Claims — deterministic, idempotent, sandboxed

> **Status:** implemented 2026-08-26 ([#677](https://github.com/NobleFactor/devlore-cli/issues/677)). A provider
> method states the guarantees it makes; codegen and a type-checked pass hold it to them. Companion:
> [`3.6-method-classification.status.md`](3.6-method-classification.status.md).
>
> **This document replaced a design that never shipped.** Its first draft classified methods into three exclusive
> tiers — `pure` / `query` / `action` — and §8 records why that was rejected. The reasoning is kept because the
> tiers are an obvious idea and someone will propose them again.
>
> **Relationship to the neighbours.** [`3.2-projected-provider-api.md`](3.2-projected-provider-api.md) describes
> what a provider's methods look like once projected into Starlark, and
> [`3.3-static-starlark-codegen.md`](3.3-static-starlark-codegen.md) how the projection is generated. **This
> document owns what a method promises and who checks it.**
> [`2.4-hermeticity-guarantees.md`](2.4-hermeticity-guarantees.md) states the guarantee these claims exist to
> make enforceable.

## Thesis

**A claim is an assertion by the author, and something must be able to contradict it.**

That is the whole design. Everything else follows: claims are written by hand because only an author knows what a
method promises; they are checked mechanically because an unchecked assertion is a comment; and a false one fails
the build rather than appearing in a report, because a guarantee nobody enforces is not one.

The one thing *not* claimed is the one thing a signature already proves. A method returning a receipt mutates by
construction — [`op.Method.Mutates`](../../pkg/op/method.go) reads it from `MethodKind` — and a signature cannot
drift without changing. Everything else is asserted.

## 1. The three claims

```go
// +devlore:claim=deterministic, idempotent, sandboxed
```

| Claim | Asserts | Checked by |
| --- | --- | --- |
| `deterministic` | its output is a function of its declared inputs alone | `pkg/op/claimcheck`, against the call graph |
| `idempotent` | re-application converges to the same state | nothing static — a test obligation ([#691](https://github.com/NobleFactor/devlore-cli/issues/691)) |
| `sandboxed` | every filesystem operation routes through an `fsroot.Dir` | `pkg/op/claimcheck`, against the call graph |

Comma-separated on one line, following the `+devlore:defaults` precedent. Sorted on emission, so a regenerated
file never churns on the order an author happened to write them in. The empty set is the fail-closed default: a
method claiming nothing is admitted nowhere that requires a guarantee.

**Declared inputs**, for `deterministic`, are the method's arguments, values supplied to the
[`RuntimeEnvironment`](../../pkg/op/runtime_environment.go) at construction, and the contents of the `fsroot.Dir`
it was handed. `platform` is the illustration: it claims `deterministic` while reporting the host's OS and
architecture, because those values were *supplied* through `WithPlatform` — the syscalls happened once, in
`Detect()`, in the host application. Had it read the host per call it could claim nothing.

**They are three claims and not one enum** because they are independent and span different methods.
`idempotent` applies to *mutators*, which can never be `deterministic`. `sandboxed` and `deterministic` imply
neither direction: `regex.match` is deterministic and does no I/O at all, while a method reading a file inside a
sandboxed root that changes mid-run is sandboxed and not deterministic.

## 2. Why claims are asserted and not derived

The generator could compute most of this. It should not.

**A derived property flips silently.** If a helper three calls down grows a dependency on `os.Getenv`, inference
quietly re-classifies its callers and nothing surfaces. A claim breaks the build and names the method. The check
therefore **enforces a contract rather than discovering a value** — which is why the same analysis, run as an
inference, would be worth much less.

Mutation is the deliberate exception, for the reason given in the thesis.

## 3. What the checks are, and what they cost

### 3.1 Codegen: the shape check

`generate.star` refuses a claim its signature already contradicts, and quotes the signature back:

```
method Mkdir: claims deterministic but returns "(*Directory, *Receipt, error)",
which mutates by construction
```

Cheap, total, and local. It cannot tell whether a claim is *true* — only whether it is *possible*.

### 3.2 `pkg/op/claimcheck`: the reach check

Whether a claim is true needs the call graph, and the call graph needs types. It runs as a conformance test, so
`make check` gates it, and it loads the module once through `x/tools/go/packages` — one type-checked load rather
than one per provider during codegen.

**Types, not syntax, and the difference is not academic.** `os.Getenv` and `os.FileMode` are the same shape to a
parser, and `os.FileMode(mode)` is a *call expression* despite being a conversion. Ten methods in the `file`
provider reference `os.FileMode`, `os.O_CREATE`, `os.O_TRUNC`, `os.ErrNotExist`, or `os.ModeSymlink`; a syntactic
scan flags every one, and a type-checked one sees a type, three constants, and a sentinel. `file.Copy` carries
four and passes clean.

**The forbidden set is a denylist, never an allowlist.** Eleven packages — `crypto/rand`, `math/rand`, `net`,
`net/http`, `os`, `os/exec`, `os/signal`, `os/user`, `runtime`, `syscall`, `time` — enumerating the ways a Go
program reaches outside its own process, which the operating-system interface fixes. An allowlist of safe
packages would need roughly twenty-six entries today and would grow with every import; measured across the
twenty providers, the ratio is why.

### 3.3 Propagation, and what it cannot do

A claiming method's calls into in-module functions are followed transitively, reporting the hop chain:

```
method plan.AssembleDefinition: claims deterministic but reaches time.Now at graph.go:152,
through op.NewGraph
```

**Two boundaries are declared and never walked through.** `pkg/fsroot` IS the sandbox, so its own body calls
`os.OpenRoot`; walking it would report the sandbox as an escape from itself. `pkg/assert` reaches
`runtime.Callers` only to render a frame while raising — the abort path of a failed assertion, reachable from
nearly everything statically and running only as the process dies.

**A method on a foreign value is not an acquisition.** `f.Stat()` on an `*os.File` obtained through the root is
already confined; what would escape is *obtaining* the handle, a package-level call. Methods of ours are followed
regardless, since `p.lstat(...)` is how a provider reaches most of what it reaches.

**Interface dispatch is not followed and cannot be.** `action.Do(...)` resolves to an interface method whose
implementation dispatches by reflection, so no static walk reaches what it runs. Propagation catches a helper
that reaches a capability and never one reached through dispatch — **so a claim remains an assertion the author
is accountable for, not a proof.** `plan.Run` carries no claim because it was withheld, not because anything
verified it.

## 4. Surface eligibility is a different question

Claims say what a method promises. They do not say where it appears.

**A graph accepts anything with an action signature** — `newAction` switches over all five `MethodKind` values,
so every provider method qualifies. **A module surface is filtered per method, per runtime**, by the kind of
runtime being built:

| Runtime | Admits |
| --- | --- |
| hermetic (graph planning) | methods claiming `deterministic` |
| non-hermetic (scripting, `star`) | everything |

`file` is why this cannot be a provider-level property: a hermetic runtime wants `file.join` and not
`file.write_text`, and no bit on the provider can say that.

`+devlore:surface=` declares the two exceptions, and they are opposites: **`flow` is graph-only** — its methods
*are* the graph combinators and mean nothing outside a graph — and **`plan` is module-only**, there being no
scenario for planning the planner. Absent, a provider is eligible for both. The value maps onto `ProviderRole`'s
dispatch zone, so `RoleModule` now means *eligible for a module surface* rather than *immediate mode*.

The composition with `+devlore:root=true`, which sets the orthogonal placement bit:

| `+devlore:surface=` | Roles | with `+devlore:root=true` |
| --- | --- | --- |
| *absent* — the default | `RoleModule\|RoleAction` | `RoleModule\|RoleAction\|RoleRoot` |
| `graph` | `RoleAction` | `RoleAction\|RoleRoot` |
| `module` | `RoleModule` | `RoleModule\|RoleRoot` |

**Root applies to every surface the provider reaches**, from the one bit. `flow` is `surface=graph`, so its
root placement shows only under `plan.*`; `ui` holds both dispatch bits, so `+devlore:root=true` gives a script
`note(...)` *and* a graph `plan.note(...)`. Intended: a name is promoted because it reads better without its
qualifier, which is as true of a graph as of a script.

`starlarkbridge.Hermetic()` applies the filter at install time. A provider with nothing to offer is skipped in
silence; a provider whose every method is refused installs with each attribute denied, so the author hears about
it where they reached for it — `shell.exec is not available in this runtime: this runtime is hermetic and the
method makes no deterministic claim` — rather than at construction, which could name only the provider.

## 5. Expressibility — a property on a different axis again

A claim answers *what does this method promise*. It does not answer *can an author call it at
all*, and those are independent.

**Every resource in the tree currently publishes methods no script can invoke.** They resolve as attributes
and fail one layer deeper, at parameter binding:

```
r.can_convert_from(source="string")
→ param source: string value is neither assignable nor convertible to reflect.Type
```

`file`'s four variants announce `can_convert_from` / `convert_from`; `mem` and `function` announce
`can_convert_to` / `convert_to` / `init`. Their parameters are `reflect.Type` and `*starlark.Thread` — Go
concepts with no Starlark representation, so `op.Convert`'s cascade exhausts every step and reports a
framework internal to an author who never mentioned one.

**This is worse than a missing operation.** A missing one fails immediately and legibly. These resolve, would
appear in any generated reference as available
([#675](https://github.com/NobleFactor/devlore-cli/issues/675)), and fail late.

### Why a claim does not catch it

A framework callback promises nothing an author cares about, and stays announced anyway. `CanConvertFrom` exists
for `op.Convert` to call across a package boundary — it is Go-visible because the framework needs it, not
because an author does. **Go's `exported` is doing double duty**: *reachable by the framework* and *callable
by an author* are different sets, and the language cannot distinguish them.

Today only `SKIP_METHODS` does — a hand-maintained list of ten names that catches `Pack` and `Unpack` but not
`ConvertTo`, `CanConvertFrom`, or `Init`. Every hand-maintained surface in this repository has been found
wrong; this one is no exception.

### The rule

**A method whose parameters cannot cross the bridge is not part of the authoring surface.**

Derived, not annotated — the one place derivation is right, for the reason §2 gives. The
bridge already owns the answer: `op.Convert`'s cascade *is* the definition of what can cross, and §6 shows
both dispatch modes bottom out in it. Asking it is correct by construction and cannot be forgotten, because a
new callback taking a `reflect.Type` is excluded the moment it is written.

It also disposes of the boundary case cleanly. `Equal(other any)` stays: `any` accepts anything Starlark
produces, and `a.equal(b)` is a reasonable thing to write.

**Emitted like the claims** (§1), so a method leaving or entering the authoring surface shows up in
a diff rather than silently.

### Relation to §7

Unlike the cases in §7, this is not something the scheme cannot express — it is a property the scheme was
not asking about. Adding it needs no new annotation and no new judgment call, only a question put to a
component that already exists.
## 6. The two dispatch stacks converge in `op.Convert`

Distilled from the retired stack-comparison sketches (2026-08-20; their line-level stacks described a
superseded shape — `NodeBuilder`/`task_builder.go` no longer exist — but the law they proved still holds and
is worth keeping):

**Both dispatch modes bottom out in `op.Convert`'s single seven-step cascade** (assignable/convertible →
slice recursion → map recursion → `SourceConverter` → `TargetConverter` → registered resource construction →
error). Immediate mode (`goReceiver.dispatch`) unpacks Starlark values to natural Go and converts per
parameter inside `Method.Invoke`, at dispatch time. Plan mode (`ActionPlanner.Plan`) converts at
slot-binding time. There is no duplicate type-matching anywhere — one cascade, two entry points.

**The asymmetry that remains is deliberate**: plan mode converts at slot-fill so the catalog can intern
resources before the node is sealed; immediate mode converts at dispatch because immediate receivers pass
raw values and cataloged resources are a planning concern
([4-resource-management.md](4-resource-management.md) §9 item 3). Same cascade, different timing — the
timing difference *is* the plan/immediate distinction, seen from the converter.

## 7. What claims cannot express

**`template` cannot claim `deterministic` while its function map holds `"Env": os.Getenv`.** Purity depends on the
*template text* rather than on the method:

```
template.render_text(content="hello")               deterministic
template.render_text(content="{{ Env \"USER\" }}")  machine-dependent
```

No per-method claim can express that. Filed as [#683](https://github.com/NobleFactor/devlore-cli/issues/683):
`Env` should consult declared runtime variables, the way `make` does, rather than the ambient environment. Once it
does, every value it can reach is a declared input and the method claims like any other.

**Four methods read machine-local configuration while planning.** `file.Find`, `file.Glob`, and `file.WalkTree`
reach the global gitignore; `encryption.EncryptFile` reaches the SOPS config. Both go through `xdg.ConfigPath` to
`$HOME`, outside any root, so all four had to give up `sandboxed`. The reads are legitimate; the claims were not.
[#694](https://github.com/NobleFactor/devlore-cli/issues/694) asks the real question — how configuration reaches a
planning run at all — against the position that the framework should read none of it, and the application should
supply it as an input.

**Root contents are not frozen.** A method reading through a sandboxed root is bounded, but `2.4`'s temporal
guarantee is a property of the run, not of the method: nothing stops a file changing between two reads. So
`sandboxed` never implies `deterministic`, and the walkers could not claim the latter even with the config
question settled.

## 8. Why the three tiers were rejected

The first draft of this document classified methods as `pure` / `query` / `action` — one exclusive tier per
method, with namespace placement and hermeticity both derived from it. Design review on 2026-08-26 rejected it.
The reasoning is kept because the tiers are the obvious first idea: anyone asked to classify methods by effect
arrives there within a minute, and the reason they fail is structural rather than cosmetic.

### The reason: a method has several of these properties at once

**The tiers were exclusive. The properties are independent.**

`file.mkdir` is sandboxed, it mutates, and it is probably idempotent. Three facts, none implying another. A tier
holds one, so any assignment discards two true things about the method.

`idempotent` is the proof, because under tiers it could not exist at all. It applies to **mutators** — the very
methods a tier scheme labels `action` and stops describing. There is no arrangement of `pure` / `query` /
`action` that also says *and re-applying it converges*, and no renaming rescues that.

Claims compose; a tier cannot. That is the whole of it, and it is why the replacement is a namespace rather than
a better-named enum.

### A secondary problem: the name collided

Every provider method is an action. `op.Action`, `op.FallibleAction`, and `op.CompensableAction` are all actions,
and `newAction`'s switch is total over them — so a tier called `action` competes with the word that already means
*unit of work in the graph*. Real, but a rename would have fixed it. Recorded so the collision is not rediscovered
as though it were the reason.

### What is NOT a reason, recorded to stop it being repeated

During review it was argued that the tiers **misclassified `platform` and `ui`** — that `platform.os()` would be
called a host read and `ui.print()` an effect, when both are hermetic.

**That was an analysis error, not a flaw in the scheme.** `platform.os()` reads a value supplied to the runtime
environment at construction, so under `pure` / `query` / `action` it classifies correctly as `pure`; the taxonomy
could express it. What went wrong is that it was *assumed* to read the host without reading
`pkg/op/provider/platform/provider.go:71`, which delegates to a field. The same mistake was made about `ui`, and
corrected the same way.

It is written down because a rejection record that credits a design flaw for an analyst's mistake teaches the
wrong lesson: it invites the next reader to distrust taxonomies in general, when the actual lesson is narrower and
more useful — **read the implementation before classifying it.** Two providers were described wrongly for hours
on an assumption that one file would have settled.

### A third consideration, which the tiers could have survived

Mutation is not always compensable. Roughly eight methods mutate without returning a receipt — `shell.exec`,
`powershell.exec`, `git.checkout`, `git.pull`, `pkg.update`, `plan.run`, `plan.save_definition`,
`elevator.elevate` — so "receipt implies mutation" is sound while "mutation implies receipt" is false. That breaks
the *free inference* the tiers relied on, not the tiers themselves: the eight exceptions could have been
annotated. Recorded because the asymmetry outlived the scheme — it is why §1 derives mutation from the signature
and claims everything else.

## 9. Open questions

1. **Nothing claims `idempotent`** — [#691](https://github.com/NobleFactor/devlore-cli/issues/691). The claim is
   declared, parsed, and emitted, and no method carries it, because idempotency has no static evidence and an
   unbacked claim is a comment.
2. **How does configuration reach a planning run** — [#694](https://github.com/NobleFactor/devlore-cli/issues/694),
   which four withdrawn `sandboxed` claims are waiting on.
3. **Does expressibility gate or warn?** (§5) A method leaving the authoring surface is a breaking change to an
   author, whether or not it was ever callable.
