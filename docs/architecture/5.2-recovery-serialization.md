# Recovery Stack Serialization & Restart

The core mechanism — the `Trace` journal and `ResumeExecutor` — landed with the graph-immutability work (phase-8
[graph-immutability.md](../plans/extract-starlark-from-op/phase-8/graph-immutability.md)). The `FailedCompensation`-terminal restart contract below extends it; see
[compensation-failure-contract.md](../plans/extract-starlark-from-op/phase-8/compensation-failure-contract.md).
The *Design Surface* subsections further down predate that landing and are kept as exploratory notes.

## Problem

When a phase fails and retries are exhausted, the executor unwinds the recovery
stack and the process exits. The operator has no option to inspect the failure,
fix the root cause, and resume execution from the point of failure. The graph
and its accumulated state are lost.

## Restart Scenario

1. Phase N fails after exhausting retries
2. Executor offers: abort (unwind) or pause (save state)
3. Operator chooses pause — executor serializes execution state to disk
4. Operator troubleshoots (fixes config, restores connectivity, etc.)
5. Operator invokes restart — executor loads saved state and resumes from Phase N

## The Journal — `Trace` and `FailedCompensation` Restart

The journal is **`Trace`** — a serializable projection of the executor's per-run state: the `GraphChecksum` (which
graph it was taken against), the `RunStatus` (the run-status `{Phase, Condition, Reason, Message}`), the `RecoveryStack`
of per-dispatch receipts (audit + compensation, which subsume the separate results map below), and the resolved
variable map. The trace additionally carries the **run-status transition journal** (settled 2026-07-05; realization:
phase-8 step 41) — `{Phase, Condition, At, UnitID, Reason}` per flip of either dimension, written by a single
recording setter, with the status remaining the O(1) answer. It answers "when did the run flip to
degraded?" and "where did it flip to execution_failed?" directly; per-event detail (every degradation, every
failure, every compensation outcome) stays
on the receipts, cross-referenced by `UnitID` — ReceiptBase's UUIDv7 transaction IDs already carry issue time. Restart is
**`ResumeExecutor(graph, spec, trace)`**, which reconstructs an executor from the graph + trace and refuses a
checksum-mismatched graph.

A run ends in one of the derived terminals — `{completed, stopped} × Condition` (two terminal phases, settled 2026-07-06: `completed` = the natural end with Condition exactly as it stood; `stopped` = the commanded or policy-driven end) (see
[§2.2 Phase Execution](2.2-phase-execution.md)). A `stopped × execution_failed` trace is archival (clean rollback, consistent state).
The restartable case is **`FailedCompensation`** — an unhandled failure whose unwind *itself* failed, leaving the system
half-changed. There the contract is fixed: **fail loudly, persist the `Trace`, and emit restart instructions**
(which node failed, which `Compensate` failed and why, and the resume command).

Resume from a `FailedCompensation` trace is a **state-checked unwind**, not a forward retry. The `RecoveryStack` names the
candidate set (units touched, compensations not yet succeeded); the resumed unwind **re-queries each resource's
actual state before acting** and undoes only what is still present — so it is robust to whatever the operator
cleared by hand while fixing the blocker (observe, don't assume). A clean resumed unwind lands the run at `execution_failed`
(clean baseline); it does not auto-retry forward by default.

## Framework vs. client, and journal retention (settled 2026-07-13; phase-8 step 21)

The `FailedCompensation` response splits along the framework/client boundary. **The framework reports what it
knows — the source of the problem and the compensation diagnostics — durably on the `Trace`.** **The client owns
persistence and presentation:** `internal/cli.WriteTrace` writes the `Trace` under the receipts directory, and
rendering restart instructions (troubleshooting text, the resume command) is the consumer's surface. So the
framework never calls `WriteTrace` and never formats operator prose; its whole job is to make the trace faithful.

Reporting durably has one hard requirement the executor did not meet: **the journal must survive the unwind.**
`RecoveryStack.Unwind` is best-effort-complete (R3) and, on a *clean* unwind, clears its entries — the run is back
at its pre-run baseline, so there is nothing to journal. But on a *failed* unwind it must **retain** the entries:
the failing node's receipt (the source — its forward error, nil compensator, kept as an audit entry) plus every
attempted compensation. Each compensation outcome rides its own receipt as **`compensation_error`** (a
`ReceiptData` field, `omitempty`, nil ⇒ compensated), restored uniformly by `ReceiptBase.Restore` /
`RestoreEncoded` so no provider changes — the concrete form of "every compensation outcome stays on the receipts"
above. It is distinct from the receipt's forward `status`: `status` says the forward call failed,
`compensation_error` says its undo failed. A nested substack's dirtiness is represented by its retained failed
children; the recursion needs no substack-level field.

The contract's third per-entry category — **not-yet-reached** — cannot occur at the stack level (the best-effort unwind
attempts every entry); it is a derivable journal category (planned nodes that never dispatched, which `Trace.Summarize`
tallies as `skipped`), a client concern.

## Uniform recovery-stack serialization (settled 2026-07-12; phase-8 step 42 slice 3)

The recovery tree serializes with **no `kind` tag, no stack-owned envelope, and no special cases.** The trace *is* the
root `RecoveryStack`, and every stack — root, subgraph, gather, gather-item, any nesting — serializes the same way: its
stamp (`unit_id` / `result` / `result_type` / `status`) plus `entries`. Each entry's compensator serializes *itself*:

- a `*RecoveryStack` recurses through the same method;
- a receipt encodes via `ReceiptBase` (the common resume state every receipt embeds — `unit_id`, `forward_action`,
  `compensating_action`, `result` / `result_type`, `status`, `transaction_id`) plus whatever the concrete type that
  embeds it adds (its id references — e.g. `file.Receipt`'s `resource_id` / `kind` / `recovery_id` / `recovery_digest`).
  The per-receipt compensator is **not** serialized — the tree nests it structurally — and `file` drops `resource_uri`
  in favour of `resource_id` (a catalog id pins the exact generation a shadowed URI cannot).

Reconstruction discriminates **structurally**: a node carrying `entries` is a `RecoveryStack` (recurse); otherwise it is
a receipt, whose *concrete* type is resolved from `compensating_action` (`CompensatingActionByName` → `compensatorType`)
and rebuilt via `Receipt.RestoreEncoded`. A subgraph is *itself* a `RecoveryStack` (pushed as its stamped stack, not
wrapped in a `ReceiptBase`), so it rolls back through `Unwind`, not a named companion — the subgraph-direct-push this
design requires.

Sample (YAML) — a run that linked a file, ran a nested subgraph (one `mkdir`), then a two-item `flow.gather` (each item
writing a file):

```yaml
# the trace is the root RecoveryStack: {stamp?, entries}
# `result` is the operation's output (replayed for promise resolution on resume); `result_type` is its Go type
# (retypes the reloaded, untyped value). A Choose decision's branch is re-derived from `result` by a trivial IsTruthy
# on resume — the outcome is never stored (phase-8 step 42 slice 2c).
entries:
  # leaf receipt — no `entries` ⇒ a receipt; `compensating_action` names the concrete type on reload
  - unit_id: link
    forward_action: file.link
    compensating_action: file.compensate_file_mutation   # ⇒ *file.Receipt
    result: {uri: "file:///work/a.txt"}   # ← the output
    result_type: file.Resource
    transaction_id: 018f2c3d-…   # base fields ride every receipt (the base owns transaction_id)
    resource_id: res-a           # file.Receipt's own fields (resolved via the catalog at resume); no resource_uri
    kind: create_file
    recovery_id: rk-01           # present only when the link displaced prior content
    recovery_digest: sha256-4f…
  # subgraph — has `entries` ⇒ a RecoveryStack; `result` = its body's terminal output; rolls back via Unwind
  - unit_id: subgraph
    result: {uri: "file:///work/dir"}
    result_type: file.Resource
    entries:
      - unit_id: mkdir
        forward_action: file.mkdir
        compensating_action: file.compensate_file_mutation
        result: {uri: "file:///work/dir"}
        result_type: file.Resource
        transaction_id: 018f2c3e-…
        resource_id: res-b
        kind: mkdir
  # gather — a RecoveryStack of per-item substacks; `result` = []T of the per-item outputs
  - unit_id: gather
    result: [{uri: "file:///work/c0.txt"}, {uri: "file:///work/c1.txt"}]
    result_type: "[]file.Resource"
    entries:
      - unit_id: gather#0
        result: {uri: "file:///work/c0.txt"}
        result_type: file.Resource
        entries:
          - unit_id: write#0
            forward_action: file.write
            compensating_action: file.compensate_file_mutation
            result: {uri: "file:///work/c0.txt"}
            result_type: file.Resource
            transaction_id: 018f2c3f-…
            resource_id: res-c0
            kind: create_file
      - unit_id: gather#1
        result: {uri: "file:///work/c1.txt"}
        result_type: file.Resource
        entries:
          - unit_id: write#1
            forward_action: file.write
            compensating_action: file.compensate_file_mutation
            result: {uri: "file:///work/c1.txt"}
            result_type: file.Resource
            transaction_id: 018f2c40-…
            resource_id: res-c1
            kind: create_file
```

This shape is **implemented** (phase-8 step 42 slice 3b, 2026-07-12): `RecoveryStack.MarshalYAML` emits each entry's
compensator directly and the decoder discriminates on `entries`; the stack-owned `receiptEnvelope` is gone; the trace
save/load/resume suites round-trip it. The `file`/`pkg`/`service` receipts embed `ReceiptData` in their `MarshalYAML`;
`encryption`/`git` inherit it. A Choose decision's branch is **not** serialized:
it is re-derived from the decision node's (round-tripped) `result` by `IsTruthy` on resume (phase-8 step 42 slice 2c), so
no per-entry `guard` field exists. The earlier *Recovery Stack Serialization* note under Design Surface (the `Compensator
is any` / `GatherComplement` sketch) is superseded by this.

## Design Surface

### RetryPolicy Extension

RetryPolicy gains a `pause` (or `manual`) backoff strategy. When a phase fails
and the policy specifies `pause`, the executor saves state and yields to the
operator instead of unwinding. This fits within the existing retry contract —
it's a backoff strategy that waits indefinitely for human intervention.

```go
const (
    BackoffNone        BackoffStrategy = "none"
    BackoffLinear      BackoffStrategy = "linear"
    BackoffExponential BackoffStrategy = "exponential"
    BackoffPause       BackoffStrategy = "pause"  // yield to operator
)
```

### Recovery Stack Serialization

For restart to work across process boundaries, the recovery stack must
round-trip through YAML/JSON:

- RecoveryEntry references a Node (by ID, not pointer) and stores Compensator
- Compensator is `any` — providers must ensure their state marshals correctly
  (this constraint already exists for receipts). **Refined 2026-06-26:** a
  compensable method's compensator is restricted to a concrete `*Receipt` or a
  `*op.RecoveryStack` — the `[]Receipt` shape is being removed. Concrete because
  resume reconstructs a receipt by `reflect.New`-ing the type read off its
  `Compensate` companion, which an interface or slice cannot supply. See the
  phase-8 step-31 doc's *Compensator-shape restriction* section. **Refined
  2026-06-27:** a receipt also **names its own compensation companion** (set at
  production, not derived from the dispatching action), so a receipt built by one
  provider compensates correctly on any stack — see the phase-8
  *file-mutation-receipts* design.
- GatherComplement includes per-iteration proxy contexts and recovery entries

### Results Map Serialization

The results map (`map[string]any`) holds node Results needed for promise slot
resolution. For restart, downstream nodes need access to results from
already-completed nodes. Options:

- Serialize the full results map alongside the recovery stack
- Re-derive results from the receipt (if receipts capture enough)
- Hybrid: serialize only results referenced by pending promise slots

### Execution Checkpoint

A checkpoint captures everything needed to resume:

- Graph definition (already serializable)
- Phase progress (which phases completed, which failed)
- Recovery stack (for undo if restart also fails)
- Results map (for promise resolution of remaining nodes)
- Context.Data keys that are serializable (not functions)

### Open Questions

- How does restart interact with GatherComplement? If a gather is mid-iteration,
  can it resume from the failed iteration or must it restart the whole gather?
- Should checkpoint be automatic (every phase boundary) or explicit (only on
  pause)?
- How do function-valued slots (decryptor, validators) get re-populated on
  restart? They come from Context.Data which is built from CLI flags and config.
- Does the receipt format need to change to support restart metadata?
