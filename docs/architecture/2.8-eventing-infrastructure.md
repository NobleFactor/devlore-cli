# Eventing Infrastructure: The App-Agnostic Event Bus and the Hook Interface

> **Status:** design — **proposed 2026-07-21**, under active refinement. Records the application-agnostic eventing
> infrastructure, the devlore-workflow **hook** interface that feeds it, the three output streams (narrations,
> diagnostics, operational events), and their mapping onto OpenTelemetry. Design decisions — settled and open — are at
> the end.

## Thesis

The eventing infrastructure should be valuable to **any** application, not just a devlore workflow client. It is a
general, reusable event substrate — a candidate for its own package, decoupled from devlore graphs. A devlore workflow
app reaches it through the **hook** infrastructure: the hooks are the graph app's *interface* to eventing and narration,
and they **depend on** the eventing infrastructure, not the other way round.

This sits beside [2.7 Control plane](2.7-control-plane.md) as the run's **observe** surface (2.7 is the **steer**
surface). Per [2.7 §Framing](2.7-control-plane.md#framing-three-orthogonal-pieces), a run's outward-facing surface is
three orthogonal pieces — control commands, event streams, narration — sharing one seam, the lifecycle hooks in
[`pkg/op/hooks.go`](../../pkg/op/hooks.go). This document owns the second and third pieces; 2.7 owns the first.

## The layers

1. **Eventing infrastructure** — app-agnostic, reusable. The event bus and its registered sinks. Very likely **is**
   OpenTelemetry, or a thin wrapper over it (see [Is eventing OpenTelemetry?](#is-eventing-opentelemetry)).
2. **Hook infrastructure** — a devlore workflow app's interface to eventing and narration. It **depends on** the
   eventing infrastructure. [`pkg/op/hooks.go`](../../pkg/op/hooks.go) is the seam today.
3. **Producers** — the workflow **engine** (which owns the [control plane](2.7-control-plane.md)) generates events, and
   **providers** generate events. All events route **through** the hook infrastructure.
4. **Sinks** — event sinks register with the eventing infrastructure. The **control plane** offers a sink;
   **OpenTelemetry** exporters are sinks; **filesystem logs** are a sink. One watches events via a control-plane
   request, OpenTelemetry emissions, or logs on disk.

## The three output streams

A devlore workflow app emits three distinct streams, differing in **audience** and **shape**. In the graph,
**operational events bracket the other two** — a unit's start/complete is the span within which its narrations and
diagnostics are emitted, and to which they correlate (`trace_id` / `span_id`). This bracketing may be mirrored in
`starlarkbridge`; in Starlark itself, narrations are authored **anywhere** in a unit body via `ui.Provider`.

1. **Narrations** — human-facing. Status commentary to **stderr** and results to **stdout**, by default. Today:
   [`status.Narrator`](../../pkg/status/narrator.go) (`Note` / `Warn` / `Error` / `Succeed` / `Fail`) for status, and
   `result.Pipeline` for results (`ui.note` / `ui.success` / … in Starlark). Audience: the end user running the tool.
2. **Diagnostics** — developer-facing. Detailed, operation-oriented debug information beyond status narration — the
   messages devlore **provider developers** write to troubleshoot provider code. Audience: developers debugging.
3. **Operational events** — structured lifecycle facts that **bracket** a unit's narrations and diagnostics. The ones
   identified so far are the lifecycle hooks in [`pkg/op/hooks.go`](../../pkg/op/hooks.go) (`OnNodeStart` /
   `OnNodeComplete` / `OnSubgraphStart` / `OnSubgraphComplete`), plus the run-status transitions the interface must
   gain. Audience: machines and dashboards.

## Mapping to OpenTelemetry

The three streams land on **three different OpenTelemetry signals**, not one:

| Stream | OTel signal | How it maps |
|---|---|---|
| **Status narration** (stderr) | **Logs** (INFO / WARN / ERROR) | Teed: the stderr render stays primary; a copy → OTel log (`log.iostream=stderr`). Narration vs. diagnostics is **severity**, not a custom attribute. `Note`→INFO, `Warn`→WARN, `Error` / `Fail`→ERROR, `Succeed`→INFO. |
| **Results** (stdout) | *the deliverable — not telemetry* | Results are the program's output, already captured in the trace / receipts; primary = stdout. OTel mirroring (`log.iostream=stdout`) is optional / audit-flavored, not core observability. |
| **Operational events** (hooks) | **Traces / Spans** (+ derived Metrics) | The natural fit: `OnNodeStart`→span start, `OnNodeComplete`→span end (status / error); a subgraph is a parent span; the run is the root span. The span tree **is** the execution tree. Discrete transitions (phase changed) are span events or `event.name` log records; counts / durations are derived metrics. |
| **Diagnostics** | **Logs** (DEBUG / TRACE) | Subsystem classification via the **instrumentation scope** (logger name, e.g. `devlore.provider.git`), plus `code.function.name` and the `trace_id` / `span_id` of the enclosing node span (auto-injected via context). |

**The unifying mechanism:** operational events as **spans** create the trace context that stitches narration and
diagnostics to the exact node. Pivot from a slow or failed node span to its status narration and its debug diagnostics,
all correlated by `trace_id` / `span_id`. This is the reason to route through a shared eventing infrastructure rather
than three disconnected streams.

## Narration vs. diagnostics — the audience split

> **Waiting on this section — the module-selection report.** `starlarkbridge.Runtime.reportSelection` narrates
> what a runtime's module surface admitted, refused, and never considered. It is diagnostics by this section's own
> test — a framework decision an author consults when a method is missing, not user-facing progress — but it
> narrates today because the DEBUG / TRACE diagnostics API named below does not exist yet. The call site carries
> `TODO(#507)` and moves when [#507](https://github.com/NobleFactor/devlore-cli/issues/507) lands. It is a small, concrete first consumer to design the API against.


Diagnostics (stream 3) and status narration (stream 1) are the same *mechanism* — OTel **Logs** — differing only in
**severity and audience**:

- **Status narration** — for the **end user** watching the run. Curated, sparse ("Installing X", "Deployed to Y").
  Shown by default. INFO and above.
- **Diagnostics** — for the **developer** troubleshooting. Verbose ("stat returned ENOENT, falling back…", "retry 3,
  backoff 2s"). Hidden by default. DEBUG / TRACE.

The distinction is the developer's to make — but the design should not rely on discipline alone. Two mechanisms make the
right call the easy one and wrong calls self-evident:

1. **Two distinct APIs.** `status.Narrator` stays the user-facing progress API; a separate diagnostics API
   (`log/slog`-based, DEBUG / TRACE) is the developer channel. The choice is obvious at the call site — a different
   object.
2. **A default-visibility split.** Narration is INFO+ (shown by default); diagnostics are DEBUG / TRACE (hidden until
   `-v` / `--verbose`). This makes mistakes surface immediately: debug detail written as narration **spams the user**;
   user progress written as a diagnostic **vanishes**. The feedback loop trains correct usage better than a convention.

In OpenTelemetry this costs nothing extra: narration and diagnostics are the **same Logs signal** at different
severities and categories — not separate machinery, exactly what the default-visibility rule keys off. Diagnostics is a
**new API to add**: today providers narrate through `status.Narrator`; the span-correlated DEBUG / TRACE diagnostics
channel is the piece stream 3 introduces.

## Ignored errors are diagnostics

An intentionally ignored error — best-effort cleanup, an unwind on an already-failing path, a fallback probe — is never
silent. Every such error is a **pending diagnostic**: once the diagnostics API (stream 3) lands, the site logs the
ignored error to the diagnostics stream (DEBUG, span-correlated) instead of discarding it.

Until then, every ignored-error site carries the canonical search string `diagnose-ignored-error` inside its lint
suppression, linking back to this spec:

```go
//nolint:errcheck // diagnose-ignored-error: <why ignoring is correct here>; see docs/architecture/2.8-eventing-infrastructure.md
```

**Search string: `diagnose-ignored-error`** — grep for it to enumerate every site that owes the diagnostics stream a
log call. When the diagnostics API lands, the sweep converts each site to a real diagnostics call and deletes the
suppression; the marker count reaching zero is the done signal.

### Discarded values owe the same debt

An intentionally discarded *input* — a malformed environment variable, a configuration entry rejected as invalid —
is a pending diagnostic on exactly the same terms as a discarded error. The user set something and the program
declined to use it; saying nothing leaves them to discover the difference by its absence.

Such a site has no `err` to suppress and therefore no `//nolint` comment for the marker to live in, so **the marker
goes in a plain comment at the site**:

```go
// diagnose-ignored-error: <what was discarded and why>; see docs/architecture/2.8-eventing-infrastructure.md
```

One search string, one done signal: a discarded value that hides from `grep diagnose-ignored-error` is invisible to
the sweep that closes this out.

The first instance is `pkg/xdg`, where a relative `XDG_*` variable is discarded. That one is not merely our
convention — the XDG Base Directory Specification requires it: an implementation encountering a relative path
"should consider the path invalid and ignore it", and the specification separately instructs applications to
"print a warning message" when `XDG_RUNTIME_DIR` is absent. External requirements to warn are the strongest case
for this stream existing at all.

## Is eventing OpenTelemetry?

OpenTelemetry's collectors support many forms of logging and export, so its collector / exporter pipeline already **is**
a general eventing bus with pluggable sinks. Two positions, to settle:

1. **Eventing infrastructure *is* OpenTelemetry.** Adopt OTel as the bus directly; its collectors / exporters are the
   sink mechanism.
2. **Eventing infrastructure *wraps* OpenTelemetry.** A thin devlore façade with OTel as the primary export path
   underneath.

Either way, the OTel **Collector is the router** — this **displaces a hand-built sink registry**. The app's job
collapses to emitting well-attributed OTel Logs (and spans); routing and signal derivation (metrics from event logs)
become Collector configuration. Implementation seed (per external review): `log/slog` as the primary logging API with a
tee handler (terminal locally, the `otelslog` bridge to OTel remotely); operational events as spans via the OTel trace
API; metrics derived either in-app (Metrics API) or in the Collector (log-count processor / connector); a Collector
routing table sending narration → filter → cold / filesystem, operational events → connector → time-series (Prometheus),
diagnostics → batch → log analytics.

The one channel that stays **outside** OTel: human **narration rendering** to the terminal. OTel's signals are
logs / traces / metrics — structured; the terminal render is a rendering, not a signal. Narration renders to the
terminal (primary) and may tee a **copy** to OTel as a log, but its stderr / stdout behavior is owned by the narration
layer, not by OTel.

## Filesystem persistence

Persisting telemetry to disk follows the same rule — the **Collector's `fileexporter` is the default**: the app emits
OTLP; the Collector writes files with rotation and compression, no app-side code (the "filesystem logs are a sink"
layer above). A **direct-to-file fallback** — the SDK `stdoutlog` exporter pointed at an `io.Writer` — covers
no-Collector local / offline runs; it is **fallback only** (no rotation, a single degenerate exporter), never a general
app-side routing layer, so it does not re-introduce the sink registry [decision 3](#design-decisions) rejects.

**The `stdoutlog` exporter writes structured JSON and MUST target a separate file/writer (e.g. `otel-logs.json`) —
never the program's real `stdout` or `stderr`.** Those streams are owned by the narration layer (results → stdout,
status → stderr, the one channel kept outside OTel); wiring the JSON exporter into them would corrupt human output.

## Relationship to the rest of the model

- **[2.7 Control plane](2.7-control-plane.md)** is the **steer** surface (commands) and **one sink** among several on
  the observe side — its event-watching is an eventing consumer; its command surface is separate. Not the owner of
  events.
- **[6 Execution topology](6-execution-topology.md) §Telemetry** is the transport seed for the event stream (`Event`,
  `SubscriptionManager`, ndjson-over-SSH, the elevation-and-eventing rule); it is subsumed here as the remote-transport
  instance of this bus.
- **[`pkg/op/hooks.go`](../../pkg/op/hooks.go)** is the shared emission seam — the producer-side interface for
  operational events, and the routing point for narration / diagnostics.

## Design decisions

**Settled 2026-07-23** (worked interactively; the OpenTelemetry direction corroborated by an external review):

1. **`slog` is the primary logging API** (was "Narrator / Pipeline vs. slog"). `status.Narrator` / `result.Pipeline`
   sit **above** `slog` as a **tee handler**: render locally (status → stderr, results → stdout, keyed on the `stream`
   attribute) and bridge a copy to OTel via `otelslog`.
2. **The categories are narrations, diagnostics, and operational events** (was "canonical stream taxonomy"; picks the
   external mapping over "operational logs / narrations / results"). Operational events **bracket** the other two: a
   unit's lifecycle boundary is the span within which its narrations and diagnostics are emitted and to which they
   correlate. Operational events are **both** node spans (the span tree **is** the execution tree) **and** discrete
   `event.name` records at each transition, so the Collector can derive metrics without losing the trace.
   **Frozen attribute names — OTel-native (verified against semconv 1.43.0); no invented vocabulary:**
   - **Category is carried by signal + severity, not a custom attribute** — operational events are **Traces/Spans**
     (+ `event.name` records); narrations and diagnostics are both **Logs**, split by **SeverityNumber** (narrations
     INFO / WARN / ERROR, diagnostics DEBUG / TRACE — the default-visibility split).
   - `event.name` (OTel event attribute) — on operational-event records: `node.start` | `node.complete` |
     `subgraph.start` | `subgraph.complete` | `run.status.changed`. The values are devlore's; the mechanism is OTel's.
   - `log.iostream` (OTel) — `stdout` | `stderr`; narration status → `stderr`, results → `stdout`.
   - **Instrumentation scope** (the logger name, e.g. `devlore.provider.git`) classifies diagnostics by subsystem — the
     OTel-idiomatic replacement for a custom `log.classification`.
   - `code.function.name` (OTel, stable since semconv v1.33.0 — the fully-qualified name; `code.namespace` was folded
     into it and removed).
   - `trace_id` / `span_id` — LogRecord context fields, auto-injected from the enclosing node span (not attributes we
     set).

   *Dropped as invented (each replaced by a native mechanism above):* `event.category`, `stream: status|result`,
   `log.classification`. Any genuinely devlore-specific attribute that survives must be namespaced `devlore.*` with
   justification.
3. **Eventing = OpenTelemetry; the Collector is the router** (was "eventing or a wrapper?"). devlore emits
   well-attributed OTel signals; the Collector routes and derives — **no hand-built sink registry**. A bounded
   **in-process tap** serves the two consumers OTel does not: terminal narration rendering (stderr / stdout) and the
   control plane's live `Subscribe()` watch — same emission points, **not** OTel exporters.
4. **Metrics derivation: the Collector connector is the default** (was open). Emit the `event.name` record and let the
   Collector count / derive; reserve the in-app OTel Metrics API for counts the Collector cannot reconstruct.

5. **Hook interface reconciliation** (code-facing; implementation deferred to step 50). Keep `OnNodeStart/Complete`
   and `OnSubgraphStart/Complete`; **add** `OnRunStatusChanged(runtimeEnvironment, previous, current RunStatus)`. Do
   **not** revive `OnPhase*` — `Phase` is one axis of the settled `RunStatus`
   ([`2.2-phase-execution.md`](2.2-phase-execution.md)), not a hook name. The callback fires at the **run level only**
   (the root subgraph — the graph's status is the root subgraph's status) on **every phase/condition transition**
   (`preparing → running → pausing/paused → completed | stopping → stopped`); each maps to an
   `event.name=run.status.changed` record plus the root span's status. **Nested subgraphs** surface via
   `OnSubgraphStart/Complete` — their internal `RunStatus` folds into `OnSubgraphComplete` and their own span, not a
   scoped run-status stream. **Sub-events** (retry, compensation, pause/resume) ride as `event.name` records within
   the enclosing span, not new hook methods; the inline `emit` calls (`node.go:161`, `graph_executor.go:534–597`)
   then route through the new callback.
