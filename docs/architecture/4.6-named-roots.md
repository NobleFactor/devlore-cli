## Thesis

**An activity binds one `fsroot.Binding` for each tree it touches, and the root travels with the data.** A writ scope
is not one tree: it is a target and one tree per layer, three today and possibly more. A lore install reads its
package and writes to system, home and configuration trees. One root per run must widen until it holds all of them,
which is no confinement at all when the trees are far apart, and nothing at all when they sit on two Windows drives.
Named roots bound to the activity keep each tree confined to itself.

## 1. The problem: one root per run

Every run today opens exactly one root. `op.RuntimeEnvironment` holds one anchor and one lazily opened `fsroot.Dir`,
and its `Root()` is read in about 80 places. The pre-flight seam (`op.RootBinder`) re-binds every root-relative
resource to that one root.

```
today: one fsroot per scope run, widened until it holds every tree

  Home run   root = common ancestor (usually $HOME; / when a layer lives elsewhere)
               ├── $HOME                          target  (write)
               ├── <base snapshot>/Home           source  (read)
               ├── <team snapshot>/Home           source  (read)
               └── <personal snapshot>/Home       source  (read)
```

writ's deploy, upgrade, adopt and layer registration compute the root as `fsroot.CommonAncestor` of the trees they
touch; across two Windows drives there is none, and the run is refused. lore and star anchor at the working
directory. [#571](https://github.com/NobleFactor/devlore-cli/issues/571) records why star cannot simply anchor
wider: a volume anchor redefined every relative path in every script.

## 2. The model

Ruled by the owner, 2026-10-02.

**Binding is the model.** "a run opens one fsroot for each tree it touches: the scope, the layer, and the lore package
declare which named roots they use and in what role." A scope consists of more than one tree, "three trees and could
potentially grow from there". Lore's package is a different thing from writ's scope, "and the collection of such
things, including targets, is represented by an fsroot bound to some activity."

```
named roots: one fsroot per binding, each confined to its own tree

  writ, scope Home                          lore, package foo
    home           → $HOME             rw     package  → <cache>/devlore/…/foo   r
    base:home      → <snapshot>/Home   r      system   → /                       rw, elevated
    team:home      → <snapshot>/Home   r      config   → $XDG_CONFIG_HOME        rw
    personal:home  → <snapshot>/Home   r
```

- **The type is `fsroot.Binding`**: a root name bound to a directory, for one activity. It lives beside
  `op.Binding`, a slot's value; the owner: "it's the most clearcut use of the term we have."
- **The activity is the lifecycle operation**: deploy, upgrade, reconcile, decommission, adopt. writ runs one
  activity per scope, as today, and it applies to each `fsroot.Binding` in the role it declares. A lore activity is
  one package install, across its package, system and configuration trees.
- **The role is declared where a root is used, not fixed on the root.** Deploy reads `personal:home`; adopt writes
  it. The same tree, two activities, two roles.
- **A name says which tree, not which directory.** `personal:home` binds to a pinned snapshot when deploy runs and to
  the live repository when adopt runs. Each activity binds its own.

## 3. Providers: the root travels with the data

Ruled by the owner, 2026-10-02: "I don't see that B or C can work."

Every location a provider touches arrives bound to its `fsroot.Binding`. The location's identity becomes
`(root name, rel)`, which plan space spells `@name/rel`. The pre-flight seam generalizes from the one root to the
binding a location names: each resource binds to `bindings[its root name]`. Providers do their I/O through the
location's own bound root, and `RuntimeEnvironment.Root()` goes. The environment keeps the activity's set of bindings,
for the executor and for planners.

```
today
  planning     identity = rel                       providers ask  RuntimeEnvironment.Root()
  pre-flight   every resource: BindRoot(environment.Root())          one root for all
  execution    I/O through the resource's path, or through environment.Root()

with bindings
  planning     identity = (root name, rel)          plan space spells it  @home/.config/x
  pre-flight   each resource: BindRoot(bindings[its root name])
  execution    I/O through the resource's own bound path; no provider asks for "the" root
```

## 4. star's immediate runtime

Ruled by the owner, 2026-10-02.

star runs scripts with no planned graph and no pre-flight pass, so **a path binds when it is created**, by one rule
that the pre-flight pass shares:

| A script writes | It binds to |
| --- | --- |
| `@name/rel` | that binding |
| a relative path | `work`, the working directory, so every relative path keeps its meaning |
| an absolute path | the deepest binding that holds it |
| an absolute path no binding holds | nothing: **refused** |

**star's default bindings**, all **reserved**:

| Name | Bound to |
| --- | --- |
| `work` | the working directory |
| `repo` | the enclosing repository's root; unbound outside one |
| `config`, `data`, `state`, `cache`, `bin` | the XDG trees (§6) |
| `scratch` | the session's private temp folder |

There is no `home` default: binding it makes nearly everything the user owns reachable. A script adds roots, mainly,
through a `roots:` section in its `extension.yaml`, each with a name, a path and a role; also through `star.roots` in
configuration, and for one run with `--root name=path`. This answers #571, whose candidate 4 is this design.

## 5. The vocabulary

Approved by the owner, 2026-10-02. One vocabulary across writ, star and lore, so that a name means the same tree in
every program.

| Kind | Names | Examples |
| --- | --- | --- |
| writ targets | the scope's name in lower case, as the record writes scopes | `home`, `system`, `programdata`, `programfiles`, `programfilesx86`, a custom `staging` |
| writ layer trees | `<layer>:<scope>` | `base:home`, `team:system`, `personal:staging` |
| star | the reserved defaults (§4) | `work`, `repo`, `scratch` |
| lore | `package` for its own tree; the shared names for its targets | `package`, `system`, `home`, `config` |
| every program | the XDG trees (§6) | `config`, `data`, `state`, `cache`, `bin` |
| plan space | `@name/rel` | `@home/.config/git/config`, `@personal:home/.config/git/config` |

## 6. The XDG bindings

Ruled by the owner, 2026-10-02. **The XDG trees are reserved `fsroot.Binding`s in every program**: writ, lore, star
and devlore-test. Each is named for its variable without `XDG_` and `_HOME`, and bound from `pkg/xdg`:

| Name | Variable | Default |
| --- | --- | --- |
| `config` | `XDG_CONFIG_HOME` | `~/.config` |
| `data` | `XDG_DATA_HOME` | `~/.local/share` |
| `state` | `XDG_STATE_HOME` | `~/.local/state` |
| `cache` | `XDG_CACHE_HOME` | `~/.cache` |
| `bin` | `XDG_BIN_HOME`, the de-facto extension | `~/.local/bin` |

The roots devlore already opens for its own configuration, state and store (`cli.OpenTree`) become these bindings.

## 7. Open

To be answered here as the lane proceeds. The plan lists the same questions.

1. **Identity's costs.** #597 lists the URI grammar, catalog keys and serialization; its precedent keeps the schema
   at 1 and lets old documents die.
2. **Undo across activities.** A receipt records its root names, but the activity that undoes may differ from the
   one that did: decommission undoes deploy's links.
3. **Operations that cross roots.** A move between two roots, as adopt does, and a link whose target lies in another
   root, as deploy makes.
4. **Where elevation attaches.** Presumably to one binding, `system`; lane 34
   ([#521](https://github.com/NobleFactor/devlore-cli/issues/521)) designs the mechanism.
5. **A binding whose directory does not exist yet**, such as a fresh install's XDG trees.
6. **`repo` without git**: the rule that finds the enclosing repository.
7. **Windows**: writ's readback and `workflow verify` anchor at `string(filepath.Separator)`, which is drive-relative
   there. This design retires it.
